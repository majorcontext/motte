# Architecture

This document is the contract for motte. A change in behavior updates this document in the same pull request.

## Goal and non-goals

Goal: motte stores the repositories of coding agents and the state of their virtual workspaces. A control plane (the caller) creates repositories, claims workspaces and flushes their state. A node daemon and the jj backend read and write objects, refs and operation logs.

Scale goals:

- Large repositories: tens of millions of objects in one repository.
- Many concurrent clients: clones, fetches, pushes, ref updates and lands run in parallel.
- Regional read replicas with a single writer. A replica serves reads in its region. Every write goes to the writer.
- Monotonic ref generations on every replica: a reader never sees a ref generation go back.
- Tenancy is per deployment. One deployment serves one tenant.

Non-goals:

- No git dumb HTTP, web UI, review or pull-request model, access lists, or users.
- No policy about review or merging. The store keeps protected ref patterns and ref events, and the caller decides what they mean.
- No purge of deleted workspaces, and no deletion of a pack that holds a live object.

## Planes

The store plane serves the node daemon and the jj backend. The control plane serves the caller. Every route needs a grant in the `Authorization: Bearer` header. The git routes also take it as the password of HTTP Basic. A grant names the repository and the workspace. No route takes either from the request.

### Service

`cmd/motte` reads its configuration from the environment:

| Variable | Meaning |
|---|---|
| `MOTTE_LISTEN` | Listen address. Default `:8080`. |
| `MOTTE_META` | Metadata backend: `postgres` or `sqlite`. Default `postgres`. |
| `MOTTE_DATABASE_URL` | PostgreSQL DSN. Required for `postgres`. |
| `MOTTE_SQLITE_PATH` | SQLite database file. Required for `sqlite`. |
| `MOTTE_BUCKET_KIND` | `gcs`, `s3` or `fs`. |
| `MOTTE_BUCKET` | Bucket name for `gcs` and `s3`, directory for `fs`. |
| `MOTTE_S3_ENDPOINT` | Optional, `s3` only. Base URL of an S3-compatible service, such as R2 or MinIO. Default: the AWS endpoint of the region. |
| `MOTTE_S3_REGION` | `s3` only. Region of the bucket. Default: the region of the AWS SDK default chain. Use `auto` for R2. |
| `MOTTE_S3_PATH_STYLE` | Optional, `s3` only. `true` addresses the bucket in the URL path, not the host name. Default `false`. MinIO needs `true`. |
| `MOTTE_TRUSTED_KEYS` | JSON list of `{"kid","key","scopes"}`. `key` is the standard base64 of an Ed25519 public key. `scopes` holds only `node`, `read`, `write`, `import`, `operator` and `merge`. The service refuses to start on any other scope text. |
| `MOTTE_OIDC_ISSUER` | Optional. The exact `iss` claim of an OIDC issuer. Turns on OIDC identities on the git routes (see Human identities). Off by default. |
| `MOTTE_OIDC_AUDIENCE` | The `aud` claim. Required with the issuer. |
| `MOTTE_OIDC_RULES` | JSON list of `{"principals","repos","scope"}`. A principal is a claim value (an email by default) or `@domain`. A `@domain` principal and a match without case apply only when the claim is `email`; any other claim matches exactly. `repos` holds repository texts such as `native:repo_X`. `scope` is `read` or `write`, or `admin` with no `repos`. Required with the issuer. The service refuses to start on any other scope. |
| `MOTTE_OIDC_KEYS_URL` | Optional. Address of the key set. Default: the `jwks_uri` of `<issuer>/.well-known/openid-configuration`. |
| `MOTTE_OIDC_HEADER` | Optional. Header that carries the JWT. Default `Authorization` (a Bearer token, or the password of Basic). Any other header carries the bare JWT. |
| `MOTTE_OIDC_CLAIM` | Optional. Claim that the rules match. Default `email`. |
| `MOTTE_OIDC_ALGS` | Optional. Comma-separated algorithms from `RS256`, `RS384`, `RS512`, `ES256`, `ES384`. Default `RS256`. |
| `MOTTE_TLS_CERT`, `MOTTE_TLS_KEY` | Optional. PEM files. When both are set the service serves TLS itself. When neither is set it serves plain HTTP for a reverse proxy, a tunnel or a local run. One without the other is an error. |
| `MOTTE_EVENT_RETENTION` | Optional. How long a ref event is kept, as a Go duration. Default `336h`. |
| `MOTTE_COMPACTION` | Optional. `true` runs maintenance of packs and layers on this replica (see Layered index and compaction). Default `false`. |
| `MOTTE_COMPACTION_INTERVAL` | Optional. The wait between maintenance passes, as a Go duration. Default `30s`. |
| `MOTTE_COMPACTION_GRACE` | Optional. How long a retired file stays before maintenance deletes it, as a Go duration. Default `1h`. |
| `MOTTE_GCS_CLIENTS` | Optional, `gcs` only. How many Cloud Storage clients share the reads, from 1 to 64. Default `8`. Each client holds its own HTTP/2 connections to Cloud Storage, so a replica holds at least this many connections. |
| `MOTTE_GCS_HEDGE` | Optional, `gcs` only. The most reads, in percent from 0 to 50, that may start a duplicate read when they are slow. Default `5`. `0` turns hedging off. |
| `MOTTE_GCS_HEDGE_MIN`, `MOTTE_GCS_HEDGE_MAX` | Optional, `gcs` only. The least and the most time, as Go durations, that a range read waits before its duplicate starts. Defaults `20ms` and `2s`. |
| `MOTTE_RANGE_CACHE_MIB` | Optional. The memory of the range cache (see Range cache), in MiB, from 0 to 4096. `0` turns the cache off. Default `256`. |
| `MOTTE_PPROF` | Optional. The address of a listener that serves `/debug/pprof`, apart from `MOTTE_LISTEN`. Off by default. `MOTTE_PPROF_CONTENTION=1` adds the mutex and block profiles. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Optional. Enables OTLP export of traces and metrics. The standard `OTEL_*` variables set the headers, the service name, the sampler (`OTEL_TRACES_SAMPLER`) and the metric interval (`OTEL_METRIC_EXPORT_INTERVAL`). |

The `s3` backend takes its credentials from the AWS SDK default chain: the environment (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`), the shared files, or a role. The service refuses to start on a `MOTTE_META` or `MOTTE_BUCKET_KIND` value that it does not know, on a `MOTTE_S3_*` variable with another kind, and on a `MOTTE_S3_PATH_STYLE` value that is not `true` or `false`. The service applies the embedded migrations of its metadata backend at start. The PostgreSQL backend applies them under an advisory lock, so replicas can start together. `GET /health` answers 200. `GET /ready` answers 200 once the service has loaded the layers of every repository, and while the metadata backend answers a ping. The service loads the layers, newest layer first, 16 at a time, and stops when they fill the layer cache of 128 MiB. When a read of an index fails, it logs the error, answers 503 and retries every 5 seconds. `GET /metrics` serves Prometheus metrics. These three routes need no grant. A request for a path or method that no route serves answers 404 `vcs_not_found` or 405 `method_not_allowed` in the error envelope.

### Run locally

The service runs with the `sqlite` metadata backend and the `fs` bucket and no other service. The key pair is any Ed25519 pair, and this command makes one and starts the service on `:8080`:

```
openssl genpkey -algorithm ed25519 -out motte.key && MOTTE_META=sqlite MOTTE_SQLITE_PATH=motte.db MOTTE_BUCKET_KIND=fs MOTTE_BUCKET=objects MOTTE_TRUSTED_KEYS="[{\"kid\":\"local\",\"key\":\"$(openssl pkey -in motte.key -pubout -outform DER | tail -c 32 | base64)\",\"scopes\":[\"node\",\"read\",\"import\",\"operator\"]}]" go run ./cmd/motte
```

The local loop of a person needs no identity provider, no tunnel and no workspace box. `motte operator-grant --key motte.key --kid local` prints an operator grant for `MOTTE_TOKEN`. With it, issue a token, and use plain `git` with it as the password; `ward check` runs the checks of the repository and `ward land` lands a branch (see README "Developing"). The service serves TLS itself when `MOTTE_TLS_CERT` and `MOTTE_TLS_KEY` are set.

A Go test starts the same composition with `testserver.StartLocal`, which needs no service and never skips. `testserver.Start` runs on PostgreSQL. It uses the database of `MOTTE_TEST_DATABASE_URL`. Without that variable, `internal/pgtest` starts one throwaway cluster for each test package when `initdb` and `postgres` are on `PATH` or in the directory `MOTTE_TEST_PG_BIN` names. The cluster listens on a unix socket only, runs with `fsync` off, counts as one process, and the package stops and removes it at the end of its tests. When neither a database nor the binaries exist, the test skips, or fails when `MOTTE_TEST_REQUIRE_PG=1`. One process uses one SQLite file and one `fs` directory.

### Load test

`motte-loadtest` has three commands. `gen` builds a repository in a running service. `run` drives clients against it and prints a report. `serve` runs a local service on SQLite and a filesystem bucket, and adds `-latency` to each read of the bucket, to stand in for an object store with a network between it and the service. `gen` builds source-like files by default. A file has whole lines, and its line count is log-normal (`-lines-median` 135, `-lines-sigma` 1.47). `-shape tree` (the default) builds a random tree of `-files` files in directories of uneven size (`-dir-files-mean` 9.3, `-dir-files-sigma` 1.5, at most `-max-depth` 8 levels deep), and `-shape grid` builds the uniform tree of `-fanout`, `-depth` and `-leaf`. Each commit of history changes 1 or more files, a log-normal count with a mean of 3.3 (`-files-per-commit N` fixes it), and a changed file keeps its other lines, as a changed region of `-change-lines-median` 8 lines (`-change-lines-sigma` 1.85). `-skew S` gives the directories, and the files of a directory, a Zipf popularity of exponent S (default 0.7), so that history has hot files as a real repository has; 0 is uniform. `-content bytes -shape grid -skew 0 -files-per-commit 4` builds the earlier repository, whose blobs are byte ranges of one corpus and are replaced whole by each change. `gen` writes the directories of the first snapshot to `shape.txt` in `-out`, and `run` reads it; without the file, `run` uses the grid of the manifest. The defaults are the figures of the Go repository at commit 91a2e921dd (5011 `.go` files outside `testdata` in 539 directories; the last 30000 commits, 26207 of which change them): a median of 135 lines, a log-normal fit of 1.47, a median of 3 and a mean of 9.3 files for each directory, 47 percent of commits that change one file, 3.3 files for each commit and 8 lines changed for each file, and 19 percent of the changes in 1 percent of the files.

`run` has two scenarios. `-scenario mix` (the default) picks each operation at random by the weights of `-mix`. `-scenario agents` makes each of the `-c` clients one agent that loops through a task:

1. Start. The agent reads the ref `-main-ref` and, with the chance `-cold-rate` (never at its first start), does a cold partial clone (`blob:none`). Else it fetches from the commit that it last saw, and an agent that has seen none starts between half and twice `-fetch-back` commits behind the tip.
2. Explore. `-explore-reads` times, the agent reads the trees on the path to a leaf directory and then 1 to 4 of its files. It takes the directory from its task cluster 7 times in 10, and else from the popularity of all agents.
3. Work. The agent makes about `-commits` commits on its own branch. A commit changes 1 to `-edit-files` files, 8 in 10 from the task cluster and the rest by popularity. The agent reads each file that it changes, and a change replaces or inserts 1 to `-edit-lines` lines (at most a quarter of the file) at a random position, and keeps the rest of the file as it was. `-edit-whole` rewrites the whole file instead. It pushes the branch every `-push-every` commits and after the last commit.
4. Land. The agent lands the commits on `-main-ref`. On a conflict it reads the ref and fetches, makes the same edits again on the new tip, in the files of the new tip, pushes the branch again over its old head, and lands again, at most `-land-retries` times. A land that times out is repeated with the same ID, at most 4 times. A land that still conflicts after the retries abandons the task.

Popularity is Zipf with exponent `-skew` over the leaf directories and over the files of a directory, and it is the same for every agent. The task cluster is `-cluster` leaf directories: one by popularity, and each other one is a sibling of it or another by popularity. `-think` is the mean pause between steps. The report adds the steps `clone`, `fetch`, `refetch`, `ref`, `commit`, `tree`, `blob`, `edit`, `push`, `land`, `retry` (the time to make the commits again after a conflict) and `task`, the counts of tasks, lands, conflicts and retries, the mean bytes of a clone and of a fetch, and the range reads of the bucket for each task. The `conf` column counts conflicts, not errors.

```
openssl genpkey -algorithm ed25519 -out motte.key
motte-loadtest serve -key motte.key -listen 127.0.0.1:8080 -latency 20ms &
motte-loadtest gen -key motte.key -out lt -objects 400000 -files 20000
motte-loadtest run -key motte.key -out lt -scenario agents -c 64 -d 3m
```

`motte-loadtest bench` runs the measurements that decide a performance change, on one host with Docker and a Google Cloud Storage bucket that the host's credentials can write. It creates no machine and no bucket. `bench arm` runs one arm, `bench pairs` runs `-n` pairs of the service binaries `-a` and `-b`, and `bench sum` summarizes the pairs of a directory. An arm starts PostgreSQL and the service (the binary of `-a`, bucket `-bucket`) with maintenance on, runs `gen`, waits until no repository has more than `-settle` layers for three samples 10 seconds apart (at most `-settle-max`), restarts the service with maintenance off unless `-compaction` is set, and runs the load client for `-d`. The service and PostgreSQL use `-server-cpus`, and the client uses `-client-cpus`. An arm writes to its own directory the argument list of the client (`argv.txt`), the run report (`run.json`), the metrics of the service before and after the run, and the CPU of the service and PostgreSQL. The run fails when the flags that the client applied (`applied_flags` of the report) differ from the flags that the arm asked for. The service reads the bucket with the credentials of the host: the service account of a Google Compute Engine host, or the file that `GOOGLE_APPLICATION_CREDENTIALS` names, which the arm mounts into the container. The layers that the summary shows are the count at the end of the settle, and the settle counts only samples taken `-settle-min` (default 40 seconds) after `gen` ended and after a maintenance pass has seen the repository. An arm waits for `GET /ready` before it takes the first sample of the metrics, and it fails when the CPU of the service or PostgreSQL cannot be read (it needs cgroup v2). A lock file (`-lock`) lets one stack run on a host at a time, and a second `bench` command on the host fails at once. In a pair, odd pairs run A first and even pairs run B first. The summary gives, for each pair, the ratio B over A of the lands per minute, the CPU of the service for each task, the reads and bytes of the bucket for each task, the p50 and p99 of each operation, the hit rates of the caches and the layers, and the median and the range of each ratio, as a table and as a JSON file. `-snapshot NAME` saves the generated and settled repository once (the dump of the database, the files of `gen` and a copy of the bucket prefix of the repository) and restores it in every later arm, so that an arm skips `gen` and the settle and both arms of a pair start from the same state. A snapshot belongs to one host. `bench clone` runs one agent whose every task starts from a cold partial clone, and prints the clone latency and the reads and bytes of the bucket for each task, which holds the clone and the steps after it. The README lists the `gcloud` commands that make and delete the host, the bucket and the service account. A run on a host decides an end-to-end change. Two arms of one binary (an A/A pair) show the spread of the metrics on the host.

### Benchmarks

The hot paths have Go benchmarks in the `_test.go` files of their packages: `internal/gitpack` (hash, inflate, delta apply), `internal/gitproto` (commit walk with and without the commit graph, tree walk, pack write), `internal/midx` (decode of a graph and of a size file, graph lookup, layer merge) and `internal/store` (lookup of an object across layers, the range cache, and `TreeBulk` with and without size files). A benchmark builds its fixture once, with fixed seeds, and resets the timer after that. It reports allocations, and where it helps a custom metric such as `bucket-reads/op` or `commit-reads/op`. Each runs in under a second at `-benchtime=1x`. A benchmark is tooling and not a contract test: `go test ./...` does not run it, and the test budgets count tests only. To compare two builds, run `go test -run='^$' -bench=. -count=10 ./internal/... > old.txt` on one, the same command on the other as `new.txt`, and `benchstat old.txt new.txt`. The change in a function that benchstat shows is a hint. The verdict on an end-to-end change is a pair of runs on a host (see Load test).

### Limits and memory

- An object has at most 16 MiB (`gitpack.MaxObjectBytes`). A put of a larger object, and a read of a larger object in an imported pack, answer 413 `vcs_object_too_large`. A caller must not store a file above 16 MiB.
- The service reads a request body completely before it takes memory for the request. A body above its route limit answers 413 `vcs_object_too_large`, whatever its content. The limits are 1 MiB for a JSON route, 8 MiB of base64 data plus 1 KiB for `PUT /v1/vcs/ops/{kind}/{id}` (the data limit is 8 MiB before encoding), and 96 MiB plus 4 KiB for `POST /v1/vcs/objects` and `PUT /v1/vcs/packs/{pack_id}`. The upload routes allow 2 minutes to read the body.
- At most 4 upload bodies are read or wait for a reservation at one time. An upload takes one of the 4 reader slots before it reads the first byte and gives it back after it reserves memory, so a fifth upload waits. A read request takes no reader slot, so a slow upload never blocks a read.
- A put has at most 100000 objects and 64 MiB of object data. A blob batch or a `has` call names at most 4096 SHAs, and a blob batch returns at most 16 MiB.
- The service keeps a memory budget of 512 MiB for requests at work. A request reserves the peak of its live buffers before it allocates them, and waits while the budget is spent. A reservation never exceeds the budget. Apart from the reader slots, the budget is the only limit on concurrency: no request excludes the others, and a slow sender holds no reservation because the body is read before the reservation. B is the length of the body. The peak of each route comes from its code path:

| Route | Reservation | At the largest request |
|---|---|---|
| `POST /v1/vcs/objects` | B, the decoded objects (3B/4), the pack body and the pack (each 3B/4 plus 2 percent), and 80 MiB for the decoder: B + 2.5B + 80 MiB | 416 MiB |
| `PUT /v1/vcs/packs/{pack_id}` | the body, the two base64 strings, the decoded pack and index, and pack verification: 3B + 96 MiB | 384 MiB |
| `PUT /v1/vcs/ops/{kind}/{id}` | the body, the Data string and the decoded op: 3B | 32 MiB |
| `GET /v1/vcs/objects/{sha}`, `POST /v1/vcs/blobs/batch` | 4 MiB at first. Before it reads an object, the request reads the size from the pack (16 MiB for an object that the pack stores as a delta, because its base is inflated first) and, when 5 times the object bytes read so far exceeds what it holds, releases its reservation and takes that larger one: the data, its base64 text and an encoder buffer that doubled once. It never holds one reservation while it waits for another. | 80 MiB, or 5 times the object bytes |
| `GET /v1/vcs/trees/{sha}` | 8 MiB at first, which holds the 6 MiB of its read-ahead. Before it reads a tree, the request reads the size from the pack index and, when 8 times the tree bytes read so far plus 8 MiB exceeds what it holds, releases its reservation and takes the larger one. It never holds one reservation while it waits for another. A reservation above the budget waits for the whole budget and does not fail. | 8 MiB, or 8 times the tree bytes plus 8 MiB |
| `GET /v1/vcs/commits/{sha}` | 4 MiB at first, and 3 times the size of the commit, read from the pack before the commit, when that is more: a delta, its base and its result | 48 MiB |
| `GET /v1/vcs/ops/{kind}/{id}` | 8 MiB of data, its base64 text and the encoder buffer: 40 MiB | 40 MiB |
| `POST /v1/vcs/objects/has` | 1 MiB | 1 MiB |
| `POST /v1/repos/{repo}/lands` | Nothing: the handler holds a body of at most 1 MiB. The leader that ends the land reserves for each batch (see Land). | 16 MiB plus 4 times the bytes that the batch holds |

  `POST /v1/vcs/objects` reads its JSON through a decoder that refuses 24 MiB of unparsed text, so one element cannot grow the buffer: it answers 413 `vcs_object_too_large`. The memory of the process is at most 4 times 96 MiB for bodies in the reader slots, plus the 512 MiB budget, plus the 64 MiB budget of tail merges, plus the 256 MiB pack cache, the 128 MiB layer cache and the 256 MiB range cache (`MOTTE_RANGE_CACHE_MIB`) the 48 MiB budget of shared bucket reads and the 16 MiB budget of duplicate bucket reads (`MOTTE_GCS_HEDGE`): 1664 MiB. Maintenance reserves its working memory from the same 512 MiB budget. The chart default request is 1792Mi.
- A lookup of a SHA probes the layers of the repository, newest layer first (see Layered index and compaction). A layer answers from memory when its filter says that it lacks the SHA, and otherwise with one read of 7 KiB. A SHA that no layer holds costs at most one such read for each layer, and the number of layers grows with the logarithm of the number of objects.

### Range cache

The service keeps the ranges that requests read from packs in one cache for all requests, so many agents that read the same hot objects make one bucket read for a range, not one for each request. A range is named by the pack, the start and the end, and a pack is named by the hash of its bytes, so a cached range never changes. A request that finds its range there makes no bucket read. Requests that ask for one range together make one bucket read, which no single request cancels, and each of them takes the bytes. That read can outlive the request that began it, so it holds bytes of a budget of 48 MiB that belongs to the service (at least 4 MiB; a read holds three times the length of its range, because the readers of the buckets keep chunks while they grow their buffer), and it waits when the budget is spent. A read looks in the cache again before it takes the budget, so a request that missed just before another request filled the range makes no read. A hit takes no lock. The cache holds at most `MOTTE_RANGE_CACHE_MIB` MiB (default 256) of allocated range bytes and 256 bytes plus the length of the pack name of bookkeeping for each range, and it drops a range larger than the whole cache. When it is full, it evicts by the CLOCK rule: a range that a hit used since the hand last passed it stays for one more pass, and a new range counts as used. The layer cache evicts by the same rule, and a hit on it takes no lock. When maintenance deletes a pack file, it removes every range of that pack from the cache, and a read that began before the deletion does not put its range back. A request keeps the bytes of a range that it holds after the cache evicts it, at most its own read-ahead buffer. The metrics `motte_range_cache_hits_total`, `motte_range_cache_misses_total`, `motte_range_cache_evictions_total` and `motte_range_cache_bytes` count it.

### Git smart HTTP

Ordinary `git` clones, fetches and pushes a repository over HTTPS. The routes need no `/v1` grant header, and the grant goes in the way that git sends credentials.

| Route | Scope |
|---|---|
| `GET /git/<prefix>/<path>.git/info/refs?service=git-upload-pack` | `read`, `write`, `merge` |
| `POST /git/<prefix>/<path>.git/git-upload-pack` | `read`, `write`, `merge` |
| `GET /git/<prefix>/<path>.git/info/refs?service=git-receive-pack` | `write`, `merge` |
| `POST /git/<prefix>/<path>.git/git-receive-pack` | `write`, `merge` |

- Repository: the URL names the repository as `<prefix>/<path>` where the grant names `<prefix>:<path>`, for example `/git/native/repo_X.git` for `native:repo_X`. The path may hold `/`. The part up to the last `.git/` is the repository. The repository of the URL must equal the `repo` claim of the grant, or the answer is 403 `vcs_repo_forbidden`. A repository that does not exist answers 404 `vcs_not_found`, so a push never creates one: the control plane creates repositories. A repository exists when it has a `repos` row (prefix `native`), or has at least one ref (any other prefix).
- Grant: the client sends HTTP Basic with any user name and a grant as the password, or `Authorization: Bearer <grant>`. A missing or refused grant answers 401 with `WWW-Authenticate: Basic realm="motte"`, so git asks for credentials or runs its credential helper. A grant of another scope for the route (a `read` grant for receive-pack) answers 403.
- Human identity: a request with no accepted grant is also tried as an OIDC JWT when `MOTTE_OIDC_ISSUER` is set, and as a per-user token (see Human identities). A grant is always tried first.
- Protocols: fetch speaks protocol v2 only (`Git-Protocol: version=2`, git 2.26 and later). The advertisement lists `ls-refs`, `fetch=filter` and `object-format=sha1`. A request for upload-pack without v2 answers 400. Push speaks v0 and v1 receive-pack with the capabilities `report-status`, `delete-refs`, `ofs-delta` and `object-format=sha1`. The dumb protocol, `shallow` and `deepen` requests, `want-ref`, `packfile-uris`, `atomic`, `push-options`, signed pushes and `side-band` on receive-pack are not offered. A filter other than `blob:none` is refused with 400.
- Ref names: a stored ref named `main` is the git ref `refs/heads/main`. A stored name that starts with `refs/` other than `refs/heads/` has the same git name. HEAD names `refs/heads/main` when it exists. A push may write `refs/heads/<name>` and any other `refs/...` name that is valid, and `<name>` must not start with `refs/`. A stored ref named under `refs/heads/` has no git name and is not listed.
- Fetch: a `want` may name any object of the repository. The service lists the commits that the wants reach and the `have` commits that it holds do not reach, walking by commit time. It takes each commit from the commit graph when a layer holds it (see Commit graph) and reads the commit object only for a commit that no graph holds. It adds the trees and blobs that those commits reach and that the trees of the edge commits (the held parents) do not hold. With `filter=blob:none` it adds no blob that a tree names, and it sends a blob that a `want` names. It never sends a delta: the pack holds whole objects, so `thin-pack`, `ofs-delta`, `include-tag` and `no-progress` have no effect. A client fetches an annotated tag that it needs with a second `want`. It answers `ready` as soon as one `have` is common, and the pack then leaves out what that commit holds. It streams the pack through side-band 1, and reads each pack through the cache of ranged reads. A read fetches the bytes that it needs and at least 4 KiB. The walk and the read of any single object read the next 256 objects in advance while they use the current 256. To read ahead, it finds the pack and offset of all 256 names in one pass over each layer, sorts the offsets in each pack, joins offsets less than 128 KiB apart into one range of at most 1 MiB, and reads at most 16 ranges, and at most 2 MiB, at the same time. The request keeps what it reads in its own buffer of at most 4 MiB, oldest out first, and a read of an object looks there before it looks in the ranges that the pack keeps for all requests. Of a joined range, the pack keeps each object from its header to the most that its inflated size allows (at least 4 KiB and at most 256 KiB), and not the gaps. It reads the rest of an object that runs past the end of its range in one more read, so the object needs no read of its own. Every read of a range of a pack goes through the range cache first. A prefetch plans at most 2 MiB of objects for each pack, and a pack keeps at most 4 MiB of ranges, where the oldest range leaves first. The walk of trees goes one level at a time, from all the roots of the fetch together: it reads the trees of the next 256 of the level in advance while it parses the current 256, so the trees and blobs of a fetch leave in level order. The pack write does not follow that order, so it reads each pack once from front to back. Before it writes the pack, the fetch drops its sets and finds the pack and the offset of every object of the list in one pass over each layer, and sorts the objects by pack and offset. An object that the pack file holds as a whole object is copied: the pack takes its stored zlib stream behind a new entry header and neither inflates nor compresses it again. The copy holds at most 64 runs at once, read or waiting, and reads each run through a reader that the pack cache does not hold, so it adds no pack to that cache. It reads the packs in runs: objects less than 128 KiB apart share a run of at most 1 MiB, the next runs are read while the current one is written, and at most 6 MiB of runs are in flight, plus 32 bytes for each object of the list, at most 16 MiB more. Before it reads the runs, the pack write drops the read-ahead buffer of the request. It finds the pack and the offset of the names in batches of 2048 names, so a batch holds at most 2048 index blocks. It reads the objects that it cannot copy 256 at a time, and reads the next 256 in advance while it writes the current ones. An entry that runs past the end of its run is read in one more read of its own. The end of a stream is where zlib ends it, found by inflating it to nowhere, and an entry whose stream does not inflate to the size of its header is not copied. An object that the pack file holds as an offset or reference delta, an object that the commit and tree cache holds, and an object that no pack of the fetch holds are read by name, inflated and compressed, after the copied objects. A pack lists the copied objects in the physical order of the packs, and the others after them. Git needs no order: `git index-pack` and `git unpack-objects` read whole objects in any order, a client reads no object before the pack ends, and the pack never holds a delta. The bulk read of a tree (`GET /v1/vcs/trees/{sha}`) reads ahead 256 trees at a time. It decodes those trees, and then reads the headers of their blobs, for the sizes, in groups of 512 blobs with at most 64 reads at the same time, so a read of 30000 entries makes a few dozen rounds of reads and not one for each tree. A group is small enough to stay in the buffer of the request until its sizes are read.
- Push: the service reads the whole request body, inflates a `Content-Encoding: gzip` body first, reads the ref commands, and unpacks the pack. A thin pack is complete: the service resolves each ref delta base from the repository. It stores the objects as one whole pack of the repository, with the SHA-256 of the stored pack as its id, and adds it to the pack listing. Every object is hashed, so the pack is checked as `PUT /v1/vcs/packs/{pack_id}` checks it. The service does not check that the objects of a new commit are connected. It checks only that the new value of a ref exists, is a commit (or a tag, outside `refs/heads/`).
- Ref update: each ref command goes, in order, through the one function `updateRef` of `internal/server/git.go`, which calls `writeRefAs` (see Protected refs) and so `meta.Store.UpdateRef`. The update is a compare and swap on the commit: `old` is the commit that the client saw, a zero `old` creates the ref and a zero `new` deletes it. A ref that is not at `old` fails that command with `ng <ref> stale info`. A protected ref, written with a `write` grant, fails it with `ng <ref> protected`. The other commands go on. There is no atomic push. The service does not tell a force push from a plain one, because git sends no flag for it: the client refuses a non-fast-forward unless it is forced, and the service accepts any update that passes the compare and swap, as git does with `receive.denyNonFastForwards` unset. The reply is `report-status`: `unpack ok` or the refusal of the pack, then `ok <ref>` or `ng <ref> <reason>` for each command.
- Limits: a push body has at most 64 MiB plus 1 MiB of commands, after gzip. A pack has at most 100000 objects, 64 MiB of inflated entry data and 64 MiB of objects, and each object has at most 16 MiB (`gitpack.MaxObjectBytes`). A command list has at most 1000 commands. A fetch request body has at most 8 MiB, with at most 10000 wants and 100000 haves. A fetch holds at most 1000000 objects and commits in its sets, and a larger fetch answers 413 `vcs_object_too_large`. A fetch has no limit on the size of the pack that it streams. A push reserves its body and 2 MiB at first: B + 2 MiB. Once it has read the commands, it adds 512 bytes for each object that the header of the pack names. Before its unpack holds more inflated bytes, I, it swaps the reservation for a larger one, in steps of 1 MiB, and so reserves B + 3I + 4 times the smaller of I and 16 MiB + 2 MiB (at most B + 192 MiB + 64 MiB + 2 MiB). Before it reads the base of a ref delta from the repository, it counts the size of the base, S, as inflated bytes besides I (16 MiB for a base that the pack stores as a delta), and does the same before it reads the object that a ref command names. It never holds one reservation while it waits for another. A fetch reserves 9 MiB at first (3 times 1 MiB for one object and its buffers, and 6 MiB for its read-ahead), 3 times the length of its request body (the body, the text of its arguments and their lists), and 128 bytes for each object that its sets hold. The read-ahead of a fetch never has more than 2 MiB in flight and keeps at most 4 MiB, in a buffer that no other request reads or changes. Before its sets hold more, at 1024 objects and then at each doubling, it swaps the reservation for a larger one. Before it reads an object that is larger than the largest so far, it swaps the reservation for one with 3 times that size. It reserves at most 6 MiB + 3 times 16 MiB + 3 times 8 MiB + 128 bytes times 1000000 objects (200 MiB), and never holds one reservation while it waits for another. The pack write of a fetch reserves its own bytes when it starts: 160 bytes for each object of its list (the name in the list and in the sorted copy, 32 for the place of the object, 48 for its run, 8 for the slot of the run in the queue, and the name of an object that it cannot copy), in slices that it allocates at their full size, and 256 bytes for each pack of the repository, and the index blocks of one placement (7 KiB for each of at most 2048 names) (the reference to the pack, its id and its entry in the map that numbers the packs), the runs that it reads ahead (6 MiB and 32 bytes for each object, at most 16 MiB more), and 3 times the largest object and 3 times the length of the request body, and the fetch keeps the larger of that and the reservation for its sets. The 3 times the largest object grows with each larger object that the write reads. The plan of the write names each pack by its id and size, and opens the pack when it reads a run, so the plan holds no cache of a pack that the pack cache has evicted. An entry that runs past its run is read as the 3 times the largest object cover. A fetch whose reservation passes 32 MiB, which is a clone of a repository of more than about 200000 objects, takes one of 4 slots first, and holds no reservation while it waits for the slot, so that clones never hold the whole memory budget. A push takes one of the 4 reader slots while it reads its body, as an upload does.
- The git routes take no part in the epoch fence. A `write` or `merge` grant moves a ref with no workspace, so a workspace that works on the same ref sees the new commit through the ref generation.

### Protected refs

Policy about which ref is special belongs to the caller. The store keeps one list of protected ref patterns for each repository text, and it applies one rule. A pattern is a ref name, or a prefix that ends in `*`: `release/*` matches every ref that starts with `release/`, and `*` matches every ref. A list has at most 100 patterns. A new repository has an empty list, so `main` is not protected.

- A ref write is a create, a swap or a delete. It comes from `PUT` or `DELETE` of `/v1/vcs/refs/{name...}` or from a ref command of a git push. A single function of the server, `writeRefAs`, performs every ref write, and it wakes the delivery worker after a write that succeeds. Any other route that moves a ref must call it, except the land: its leader moves a ref with `meta.Store.LandRef` and applies the same protection rule through `refProtected`, the function that `writeRefAs` also calls (see Land).
- A `node` grant writes a ref on the store plane under its epoch fence, as before. It compares on the generation. When the ref name matches a pattern of the repository of the grant, the write answers 403 `vcs_ref_protected` and changes nothing. The check runs before the write.
- A `write` grant writes a ref by git push with no workspace. It compares on the commit (`UpdateRef`). A push command on a protected ref fails with `ng <ref> protected`, the other commands go on, and the ref does not change. The store plane routes refuse a `write` grant. The pattern is matched against the stored ref name, which is the git name without `refs/heads/`.
- A `merge` grant writes any ref of its repository that its `refs` claim allows (any ref when it has none), protected or not, with no workspace. On the store plane it compares on the generation: `PUT` with `{expect, commit}` where `expect` 0 creates the ref, and `DELETE` with `?expect=`. No epoch is read or checked. A lost swap answers 409 `vcs_generation_conflict` with the stored ref in `details.ref`, as for a `node` write. By git push it compares on the commit, as a `write` grant does. A `merge` grant also reads refs through the two `GET` ref routes.
- `read`, `import` and `operator` grants move no ref.
- `UpdateRef` and `MergeRef` differ only in the condition: `UpdateRef` needs the stored commit to be `old` (git has no generation), and `MergeRef` needs the stored generation to be `expect`. Both take no fence, take a new generation and append one event. The event kind is the writer: `write` or `merge` for `UpdateRef`, `merge` for `MergeRef`.
- Setting the list is not ordered with a ref write that has already passed its check. A write that starts after the `PUT` of the list returns sees the new list.
- The list names no workspace and needs no `repos` row. The pattern text is checked with the ref name rule. The check of `{repo}` is the repository text rule.

### Ref events

Every create, swap and delete of a ref appends one event in the same unit as the ref write, including the `main` that repository creation writes. See Contract of meta.Store. An event has these fields:

| Field | Meaning |
|---|---|
| `partition` | 0 to 63: the hash of the repo and the ref name, modulo 64. |
| `seq` | Positive. With `partition` it identifies the event. In a partition it has no gap and follows commit order, so a consumer that keeps the last `seq` of each partition loses none. |
| `repo`, `ref` | Repository text and ref name. |
| `old`, `new` | Commit before and after. `old` is empty for a create and `new` is empty for a delete. |
| `generation` | Generation of the ref after the write. For a delete, the generation that the ref had. |
| `kind` | `node`, `write`, `merge` or `operator`: the scope of the grant that wrote the ref. The event never holds a grant. |
| `time` | RFC 3339 time of the write, from the clock of the backend. |

`GET /v1/events?cursor=C&limit=M` returns up to `M` events and a new cursor. `limit` defaults to 100 and is at most 1000. The cursor is opaque: it holds the position in every partition. An empty or absent `cursor` starts at the first event of every partition. A consumer passes the `cursor` of an answer as the `cursor` of its next call, and the route returns the events after it. An answer with no events returns the same cursor. A cursor that the route did not return, or that is malformed, answers 400 `invalid_body`. The route is for a consumer that was down. The main path is delivery to a subscription.

Ordering: the 64 partitions of a store are fixed (`meta.Partitions`). An event is identified by `(partition, seq)`. The events of one ref are in one partition and arrive in commit order with no gap. No order holds between two refs, and a consumer must not assume one. The route fills its answer from the lowest partition up, so a page can hold events of some partitions only, and later pages hold the rest.

Retention: the store keeps an event for `MOTTE_EVENT_RETENTION`, 14 days by default. A server removes older events every hour and keeps the highest removed `seq` of each partition. A read from a position below that floor in any partition that the route reads answers 410 `vcs_events_pruned`, and the consumer must read the refs again. A subscription whose cursor in a partition falls below the floor stops delivering that partition and logs an error. The operator deletes the subscription and creates it again.

Delivery is push, at least once:

- An operator registers a subscription with `POST /v1/subscriptions`: a receiver `url` (http or https, with a host and no user information, at most 2048 bytes), a `secret` of 16 to 256 bytes, and an optional `repo` filter. Its cursors start at the newest event of every partition, so it gets no history. The answer carries `cursor`, the acknowledged positions in the form of an event cursor. The store keeps the secret and never returns it.
- Every server replica runs the delivery worker. A subscription has one cursor and one lease for each partition. A worker delivers a partition of a subscription only while it holds that lease, so replicas deliver different partitions of one subscription in parallel, and the order holds in each partition. The lease is columns of the row of the partition, taken by one conditional write. It is 30 seconds, and the holder renews it before each event and while it waits. A replica that crashes loses its leases when they expire, and another replica takes over from the stored cursors. All waits and lease times use the injected `internal/clock`.
- A worker reads the subscriptions and the newest `seq` of every partition, and starts a delivery for each partition that has events above its cursor. A delivery ends when the partition is caught up. A ref write that a replica commits, and the creation of a repository or a subscription, wakes the worker of that replica at once through a non-blocking signal, so a delivery starts with no wait. A delivery that is running when the signal comes reads its partition again before it ends. A write of another replica is found by the periodic pass, which runs every second (`Poll`). The worst-case latency from commit to the first delivery attempt is therefore about 0 on the replica that wrote and one poll, 1 second, on the others, plus the time of one pass. A retry after a refusal waits for the backoff.
- A delivery reads the events of a partition above the cursor and sends them one at a time, in `seq` order. It skips an event that the `repo` filter excludes, and it moves the cursor past it. One request is `POST` of the JSON event to the `url`, with `Content-Type: application/json`. `X-Motte-Partition` and `X-Motte-Sequence` are the partition and the `seq`; the pair identifies the event. `X-Motte-Signature` is `sha256=` and the lowercase hex HMAC-SHA256 of the exact request body under the secret. The request has a limit of 10 seconds, and the worker follows no redirect.
- A 2xx answer acknowledges the event, and the worker then raises the stored cursor. Any other answer, or no answer, makes the worker send the same event again after a wait of 1 second, doubled after each attempt, up to 5 minutes. The worker sends no later event first. A crash between the answer and the cursor write repeats one event, so a receiver must treat a repeated `(partition, seq)` as a repeat. A receiver gets the events of one ref in order, and the events of different partitions in no fixed order.
- A log line of delivery names the subscription, the `seq`, the status and the type of an error. It never holds the URL, the secret or the body.

### Land

A land takes a change that an agent built on an older base, and moves a ref to a tip that holds it. The store checks file-level conflicts against what landed since that base, rebases the change onto the current tip, and moves the ref. Many agents that land on one ref at once therefore need no read, rebase and compare-and-swap loop of their own.

`POST /v1/repos/{repo}/lands` takes `{id, ref, base, head, expect_tree}` and waits for the result, so the caller never polls.

- Grant: `{repo}` is the repository text, and it must equal the `repo` claim of the grant, else 403 `vcs_repo_forbidden`. A `merge` grant lands on any ref. A `write` grant lands only on a ref that no protected pattern matches, else 403 `vcs_ref_protected`. The check runs when a new request is accepted and again when the leader runs the land, so a write that starts after `PUT` of the pattern list returns never moves a protected ref. A `node`, `read`, `import` or `operator` grant answers 401. A land takes no workspace and no epoch.
- Request: `ref` is a stored ref name. `base` and `head` are 40 lowercase hex digits. The commits after `base` up to `head` are the change. They are linear: each has one parent, and the first-parent chain of `head` reaches `base`. The objects are stored before the request: a caller puts them with `PUT /v1/vcs/packs/{pack_id}`, `POST /v1/vcs/objects` or a git push to another ref. `id` is optional, 8 to 64 characters of `A-Z a-z 0-9 _ -`. A repeat of an accepted `id` with the same `ref`, `base`, `head` and `expect_tree` returns the first result and never lands twice, and a repeat with other values answers 400 `invalid_body`. The server looks up an accepted `id` before it checks protection, so a repeat gets its result even when the protected patterns changed after the first request; only a new land meets the protection check of the request. A result is kept for 24 hours.
- Refusals that depend on the request alone: a body, `ref` or `id` that is not valid answers 400 `invalid_body`. `base` equal to `head`, a merge commit in the range, a range that does not reach `base`, a range of more than 1000 commits, and a changed path that is not valid UTF-8 answer 400 `vcs_land_invalid`. A range of more than 100000 changed leaves, a rebase that writes more than 32 MiB of new objects, and a rebase that makes one object above 16 MiB (a tree that grows too big), answer 413 `vcs_object_too_large`. A missing ref, or a missing object of the range or of `base`, answers 404 `vcs_not_found`.
- Conflict: the change touches a path that also changed between `base` and the current tip. The check is by path, and a clash of a file that both sides changed in content then gets the line merge below. A path is a leaf of the tree: a file, a link or a submodule. A change of the content or the mode, an addition and a removal each count. A rename is a removal and an addition. Two paths clash when they are equal or when one is a directory above the other, so a file that becomes a directory clashes with a change below it. A conflict answers 409 `vcs_land_conflict` with `details.paths`: the sorted paths that changed since `base` and clash with the change, at most 1000. It moves nothing, and it does not stop the other lands of its batch. The paths of the later lands of one batch include the paths of the earlier lands of that batch.
- Line merge: when a clashing path is a regular file that each commit of the change modifies, and the tip has the same mode as the change and its base, the store merges the lines of three blobs: the blob before the commit, the blob of the running tip, and the blob of the commit (`internal/linemerge`, diff3 on lines). When the lines that the two sides change neither overlap nor touch, the merged blob replaces the file, the land goes on, and the paths of the land stay the paths of the change. Two sides that make the same change merge. Else the land is a conflict as above. A path that either side adds, removes or changes in mode, a link, a submodule, a blob with a NUL byte, a blob above 1 MiB or 20000 lines, and a side that differs from its base by more than 1000 lines keep the rule by path. The merge reads no clock and no random value, so the tree of a rebase still depends only on the tip and the change.
- Expected tree: `expect_tree` is optional, 40 lowercase hex digits, else 400 `invalid_body`. When it is set, the land moves the ref only if the tree of the commit that `head` becomes equals it. Else the land answers 409 `vcs_land_stale` with `details.tree`, the tree that the land would make, and moves nothing. The check runs in the batch on the running tip, after the conflict check, so it sees the earlier lands of the batch. A stale land does not stop the other lands of its batch. A fast-forward compares the tree of `head`, and a head that is the tip compares the tree of the tip. A caller that tested a tree sets it, so the ref holds exactly the tree that it tested. The tree of a rebase depends only on the tip and the change, never on the land time, so a caller can make the tree first by a land of the same `base` and `head` onto another ref that holds the same tip. A repeat of an accepted `id` must carry the same `expect_tree`.
- Result: 200 with `id`, `ref`, `generation`, `tip` and `commits`. `tip` is the commit that `head` became on the ref, and `generation` is the generation of the ref move that holds it. The ref can move on before the answer arrives. `commits` maps each commit of the range to the commit that replaced it, oldest first, as `{old, new}`.
- Fast forward: when the head already descends from the tip, which is when `base` is the tip or the tip is a commit of the range, the ref moves to `head` as it is. `fast_forward` is true and `commits` is empty. A head that is the tip answers 200 with the current generation and moves nothing.
- Rebase: otherwise the store applies the tree changes of each commit of the range, in order, to the tree of the running tip, and writes one new commit for each. It rewrites only the directories that changed. A new commit has the running tip as its parent, the tree that results, the author line as it was, the message as it was, and every other header as it was, except `gpgsig` and `gpgsig-sha256`: the bytes change, so the signature would not hold. A `change-id` header stays. The committer keeps the name and address of the original commit, and its time is the land time in UTC (`+0000`). The land time is the time of the clock of the leader when the batch starts, and every commit of a batch has it. The same inputs and the same land time give the same commits.
- Wait: the request waits for its result for at most 30 seconds. After that it answers 504 `vcs_land_timeout`. The land stays queued and can still land, so the caller repeats the request with the same `id` to get the result. The client method `Land` allows 35 seconds unless `WithBudget` sets another limit.

Queue and leader. Any replica accepts a land. It writes the land to the queue table (`land_queue`) before it does anything else, so a crash after the answer of the write loses nothing. For each `(repo, ref)` one leader at a time drains the queue. The leader is the replica that holds the land lease of the ref, one row of `land_leases` that one conditional write takes. The lease is 10 seconds, and the leader renews it before each batch. All waits and lease times use the injected `internal/clock`.

- A batch: the leader claims up to 256 queued lands, oldest first, and lands them one after the other on a running tip, so a later land sees the earlier ones. It rejects a land that conflicts or is not valid by itself. It writes the new objects of the batch as one pack, then moves the ref once. A batch takes no more lands after its new objects reach 16 MiB, and the rest stay queued for the next batch. One unit (`LandRef`) moves the ref from the tip that the leader read to the new tip, appends the land log rows and one ref event, and ends every item of the batch, with its result. A land that moved the ref has the generation of that move. If another writer, such as a git push, moved the ref since the leader read it, the unit changes nothing, and the leader starts the batch again from the new tip, at most 8 times.
- Wake: a request on a replica that finds no leader there starts one in its process and wakes it, so a land that finds a free ref starts at once. A leader hands each result to its waiting request in the same process and does not poll the store for it. A request on a replica that is not the leader reads its item every 50 milliseconds (`LandsConfig.Poll`). A leader that finds another replica holding the lease does not end: it waits for `LandsConfig.Lease`, the longest that the lease can still run, ignoring wakes, and then claims again, so a land is found after the lease ends and the replica starts no leader at each poll. A leader that finds the queue empty for 4 polls (200 milliseconds) ends the lease. The worst-case extra latency on another replica is therefore about 250 milliseconds plus the time of the batch. The periodic pass of `Run` starts a leader for every ref that has queued lands, so a land whose requester is gone is ended too. One `landHub` owns the leaders of a server. `Server.Close` cancels them and waits until each has returned, and the server command calls it before it closes the metadata store; a leader that is in a batch when it is canceled leaves its items for the next leader and does not end them as failed.
- Warm: a request that queued a land reads the commits of its range and the trees that each commit changes, from a goroutine of its own, up to 4 MiB, while the land waits for the leader, for at most 8 lands at a time: a land that finds no free place does not warm. The leader then finds them in the object cache and makes no read of the object store for them. The reads change nothing, and a failed read is ignored. The goroutine ends with the request.
- Crash: a leader that crashes loses the lease when it expires. The next leader claims every item that is not done, including an item that the lost leader claimed and did not end, and lands it. An item lands once: the unit that moves the ref also ends its items, and it needs the lease and the old tip, so a leader that lost its lease or lost a race changes nothing, and an item that the unit ended is never claimed again. A caller that gets no answer repeats the request with the same `id`.
- Failure: a batch that fails with an error that no result can stand for, such as a failed read of the object store, is tried again. After 3 failures in a row the leader ends its items with 500 `internal_error`.

Conflict index. A conflict check needs the paths that changed between `base` and the tip. The land log (`land_log`) has one row for each landed change of a ref: the tip before it, the tip after it, and its changed paths, written in the unit that moves the ref. The paths come from the log when its rows form one unbroken chain from `base` to the tip at the start of the batch. `base` may be the old or the new tip of a row, and the latest such row counts. A chain that is broken by a write of another writer, a `base` that no row names, more than 1000 rows, or a row that kept no paths makes the check diff the tree of `base` against the tree of the tip instead. A diff is made once for each `base` in a batch. A land that changes more than 1000 paths is logged with no paths. A ref keeps its last 10000 log rows, and a unit that adds rows removes the older ones. The unit that deletes a ref also deletes the `land_log`, `land_heads` and `land_leases` rows of that ref, so a deleted ref leaves no land metadata. A path set from the log can hold a path that changed and changed back, so a log check can name a conflict that a diff of the trees would not. A land never finds a conflict in a path that did not change.

Memory. The leader reserves from its own budget of 128 MiB, not from the memory budget of requests, so it never waits behind fetches while lands wait for it. It reserves 16 MiB plus 4 bytes for each byte that the batch holds, at its start, and swaps the reservation for a larger one before it reads an object that would pass it. The bytes that a batch holds are the new objects, and the objects that the current land has read. A line merge counts three times the size of each blob that it reads. It never holds the old reservation while it waits for the new one, and a reservation above the budget waits for the whole budget. A batch stores one pack, so a repository that lands at a high rate has many small packs, and a lookup probes their layers (see Layered index and compaction). Maintenance merges the layers and compacts the packs.

Events. A batch that moves a ref appends one event, as any ref write does: `old` is the tip before the batch and `new` is the tip after it, with the generation of the move. Its kind is `merge` when a `merge` grant made any land of the batch, and else `write`. The leader wakes the delivery worker of its replica after the unit. The landed commits are the commits between `old` and `new`.

## Layered index and compaction

A repository keeps one index over its packs. The index is a list of layers, oldest first. A lookup of an object probes the layers from the newest, and the first layer that holds the name answers with the pack and the offset. Packs and layers are files of the object store. They are immutable and named by content. The list is the manifest.

Class. A layer has a class in the manifest: `m` when its packs hold only metadata (commits, trees and tags), `b` when they hold only blobs, and none when a pack may hold both. A push, `POST /v1/vcs/objects`, a land and an import store one pack with no class, and so does an older release. Only a compaction writes a layer with a class (see Pack compaction). A lookup ignores the class. A merge and a compaction take layers of one class only, so each class has its own geometric sizes. The open-pack cache evicts the oldest pack that is not of class `m`, unless packs of class `m` hold more than three quarters of the cache, and then it evicts the oldest pack of any class.

Layer. A layer is one of two files, named by its key under the prefix of the repository:

- The v2 index of one pack, key `<pack id>.idx`. A push or an import stores it, and it is the layer of that one pack. The service keeps the whole index in the layer cache.
- A layer file of `internal/midx`, key `midx/<SHA-256 of the file>.midx`. It holds one record for each copy of each object of its packs: the object name (20 bytes), the number of the pack in the pack list of the layer (4 bytes) and the offset in the pack (4 bytes), sorted by name and then by pack number. Equal records are stored once. The file ends with a directory, which a reader holds in memory: the pack list (id and size), the first record of each block of 256 records, a Bloom filter of 10 bits and 7 hashes for each record, a header with the counts, and the SHA-256 of the file. A lookup tests the filter, finds the block by the first records, and reads that block with one ranged read. The layer cache keeps blocks, so its memory follows the objects that requests use, and not the size of the layers. A layer has at most 8388608 records, and an offset of a record is at most 4 GiB less one byte.

Manifest. The manifest is a JSON document in the table `pack_manifests`, one row for each repository, with a generation that starts at 1. It lists the layers, oldest first. Each layer has its key, its number of records, the total size and the number of its packs, and, for a layer file, its size and the length of its directory. An index layer lists its pack. Every change of the manifest is a compare and swap on the generation (`meta.Store.SwapManifest`), and a lost swap reads the manifest again and applies the change again. A request reads the manifest once, so it sees one consistent set of layers for its whole life. The manifest of a repository that has packs and no manifest row is made from its pack list, one index layer for each pack, when a request first needs it.

Commit graph. A layer can have a commit graph: one file that holds, for each commit of the layer, its name, the name of its root tree, its parents, its commit time and its generation. A walk of history reads the graph, not the commit objects. The key of the graph file of an index layer is `<pack id>.cg`, and the key of the graph file of a layer file is `midx/<SHA-256 of the file>.cg`. The manifest entry of a layer names its graph (`g`) and the number of commits in it (`gn`); an entry with no `g` has no graph, and a release that does not know these fields ignores them. The file has a 16-byte header (the bytes `MTCG`, the version 1, the number of commits and the length of the overflow list, each as 4 bytes, big endian), one record of 96 bytes for each commit sorted by name, the overflow list, and the SHA-256 of all the bytes before it. A record holds the name (20 bytes), the root tree (20), the commit time (8), the generation (4), the number of parents (4), and 40 bytes of parents: for 0, 1 or 2 parents the names in order, and for more than 2 the first parent, then 4 bytes that give the offset of the other parents in the overflow list, which holds each of them as 20 bytes. A reader refuses a file whose version, size, order or checksum is wrong, and then reads the commit objects as for a layer with no graph. The generation of a commit is 1 for a root and 1 more than the largest generation of its parents; it is 0 when a parent is in no graph of the repository, and a reader treats 0 as not known. A file holds at most 131072 commits, which are at most 12 MiB of records, and an overflow list of at most 3 MiB, so at most 16 MiB; a file that would need more is not written, and a reader refuses one. A few files fit the layer cache together. A commit with more than 64 parents, or with a root tree of 40 zeros, is left out of the graph and is read as an object, as the walk of the objects reads it. A layer that would need a graph of more than 131072 commits has none. The manifest entry holds the length of the file (`gs`), so a merge and a compaction reserve from the real size. The layer cache holds a graph file whole, by the capacity of its buffer, with the layers and blocks. A load of a graph reads the length that the manifest holds and one byte more, and a file of another length is refused. A load of a graph takes three times that length from the budget of shared bucket reads (see Range cache) until it is parsed and kept, and the loads of one graph are one load; a graph that needs more than the whole budget is not used, and its commits are read as objects. A merge or a compaction that would unite graphs of more than 131072 commits writes no graph and does not read the graphs. A lookup probes the graphs of the newest layers only while their files together stay within 64 MiB, half of the layer cache; a commit in an older layer is read as an object.

- Write. An import stores the pack, its index and the graph of the commits of the pack, and then the index layer names the graph. A push, `POST /v1/vcs/objects` and a land store no graph: it would put a graph write and the read of the graphs of a tail merge into the request, and a land of a shared ref waits behind them. The commits of a push get their graph when maintenance compacts or merges their layers. An import gives no graph to a commit that its pack stores as a delta, and none to a pack with more than 64 MiB of commit data; compaction rewrites the commits whole and adds the graph. A layer merge writes one graph that holds the commits of the graphs of the layers that it merges; a layer that has no graph adds none. A compaction that splits writes the graph of the metadata pack from the commits that it rewrites, with generations; a compaction that does not split writes the union of the graphs of the layers that it replaces; a blob layer has none. A layer that an older release made has no graph until a compaction rewrites it, so a repository mixes layers with and without a graph.
- Read. The walk of a fetch takes each commit from the newest layer whose graph holds it, and reads the commit object only for a commit that no graph holds. This covers the haves, the wants that are commits and every parent of the walk. A tag or a non-commit want is read as an object.
- Files. A merge or a compaction retires the graph files of the layers that it replaces, with their layer files, and the deletion rule of retired files keeps a graph file that a manifest layer names. A merge reserves from the memory budget three times the size of the graphs that it reads, and a compaction the same, in addition to the reserve above.

Size file. A layer can have a size file: one file that holds the inflated size of each record of the layer, in the order of the layer (for an index layer, the order of its index). It lets a bulk tree read fill the size of each blob entry with no read of a pack. The key of a size file is `midx/<SHA-256 of the file>.sz`, and the manifest entry of a layer names it (`z`); an entry with no `z` has no size file, and a release that does not know the field ignores it. The file has a 12-byte header (the bytes `MTSZ`, the version 1 and the number of records, each of the last two as 4 bytes, big endian), the values in blocks of 256, each block followed by a CRC-32 of its number and its values, and the SHA-256 of all the bytes before it. A value is the size plus 1, and 0 means that the size is not known; a size of 4 GiB less one byte or more is not known. The file is about 4 bytes for each record, so it adds 14% to the 28 bytes of a record. A reader that loads the whole file refuses one whose version, length, record count or checksum is wrong, and a reader that loads one block refuses a block whose CRC is wrong; it then reads the sizes from the pack headers, as for a layer with no size file. A lookup of sizes takes the names of a bulk tree read 512 at a time, so its working set is bounded. It finds the record in the newest layer that holds the name, and takes the size from that layer only: when that layer has no size file, or the value is 0, the size comes from the pack header. The layer cache holds the whole file of an index layer, and for a layer file the blocks of 256 values that match its blocks of records; both are charged to the cache by their length.

- Write sizes. A push, `POST /v1/vcs/objects`, a land and an import store the size file with the pack, and the index layer names it. A push takes the sizes from the objects, and an import from the pack headers. A layer merge writes one size file from the size files of the layers that it merges, with 0 for a layer that has none or whose size file needs more than the budget of shared bucket reads to load (a layer of about 4 million records or more; its sizes come back when a compaction rewrites it), and writes none when no size is known. A compaction reads the size of each record from the new pack, so it adds a size file to every layer that it writes, and a layer that an older release made has sizes after a compaction rewrites it. A merge and a compaction retire the size files of the layers that they replace with their layer files, and the deletion rule of retired files keeps a size file that a manifest layer names. A merge reserves from the memory budget 4 bytes for each record, which is the buffer of its builder, and 4 more for each record of an input layer that has a size file, which the merge holds while it reads; a merge that would pass the whole budget with those reads no size file and writes none. A compaction reserves 8 bytes for each record. These are in addition to the reserves below.

Object cache. The service keeps the commits and trees of at most 64 KiB that a read or a write touched, in 64 MiB of memory, named by repository and object name. A hit takes no lock. When the cache is full it evicts by the CLOCK rule: an entry that a read or an add touched since the hand last passed it stays for one more pass, and a new entry counts as touched. A read of such an object looks there first and makes no read of the object store when it finds the object. A push and a put of objects, and so a land, add their commits and trees after they store the pack. A prefetch skips an object that the cache holds. A view that read its manifest before the object was stored, or read through a view, does not use the cached object, so a view never returns an object that its layers lack. A caller never changes the bytes that the cache returns.

Visibility. A pack is visible when a manifest lists it. A push or an import stores the pack and its index, adds the pack row (`AddPack`), and then adds an index layer to the manifest. A pack whose row exists and whose layer does not, which an older release or a crash leaves, is added to the manifest by the next maintenance pass of the repository.

Tail merge. After a write adds a layer, the writer merges the newest layers into one layer file while the next older layer has at most twice the records of the layers already taken, and the merged layer has at most 131072 records. The merge reads the records of the layers in order, writes one layer file, and swaps the manifest. It needs no object data. A tail merge reserves its working memory from its own budget of 64 MiB, not from the memory budget of requests, so a write that runs while requests hold the whole memory budget still merges its tail. A tail merge stops at the newest layer that has a graph and merges only the layers newer than it, so a write reads and writes no graph; maintenance merges the layers that have one. A failed or lost tail merge changes nothing, and a write does not fail for it. One process runs one tail merge for a repository at a time.

Maintenance. `Maintain` runs a bounded pass over one repository: it adds the packs that the manifest lacks, compacts packs, merges layers and deletes retired files. It repeats the compactions, and then the merges, until no run is left or 20 seconds have passed, so a burst of writes does not outrun it. Each step holds the repository lock alone, so a tail merge of a write can run between steps. The service runs a pass over every repository that has packs, every `MOTTE_COMPACTION_INTERVAL`, when `MOTTE_COMPACTION` is `true`. It is off by default, and the deployment turns it on after the release has run in production. Run it on the writer only. With maintenance off, writes still add layers and merge the tail, and no file is deleted. Replicas that run it repeat work and never corrupt it, because every step ends in one compare and swap.

- Layer merge. The geometric rule runs over the layers of one class at a time, layers with no class first, then class `m`, then class `b`. It picks the newest run of layers: it starts with the newest layer and takes the next older layer while that layer has at most twice the records of the run, up to 64 layers and 8388608 records. A run of two layers or more becomes one layer file of the same class. Each layer that stays is more than twice the size of all the newer ones, so a repository of N objects has about log2 N layers. A merge, and a tail merge, never makes a layer whose packs hold more than 64 MiB with an average pack under 32 MiB, because compaction takes only layers of at most 64 MiB, and a layer above that would keep its small packs for good.
- Pack compaction. The same rule runs over the total pack bytes of the layers. A run that holds at least two packs, at most 64 MiB of packs and at most 8388608 objects becomes one pack, and the rule runs over the layers of one class at a time, as for a merge. A run of class `b` is copied: the service reads each pack, checks its size and its trailer, and copies its entries in order, unchanged, into one new pack of class `b`. Delta entries stay valid, because a delta names its base by a distance or by a name. A run of class `m`, or of no class, is split by object class: the service lists the entries of each pack (`gitpack.Scan`) and gives each entry the class of its object, a delta the class of its base, and a delta whose base the pack lacks the class `b`. It writes the metadata objects whole, without deltas, deduplicated, in the order of `orderMeta` (the commits newest first, then the tags, then the trees breadth first from the root trees of those commits), as one pack of class `m` that has its own v2 index, and copies the blob entries in order into one pack of class `b`. A copied offset delta gets the distance to its moved base. When the metadata of the run, inflated, holds more bytes than the packs of the run, the service copies the run as for class `b`, and the new layer keeps the class of the run. A run that holds one class writes one pack. The run becomes one layer for each pack, and the new layers take the place of the newest layer of the run. A reader finds a metadata object in a pack of dense, recent metadata, so the walk of a recent tree reads a few ranges. The new pack keeps every entry, so an object that two packs hold is stored twice and a lookup reads one copy. Each new layer file holds one pack and a record for each name, with the offset of its first copy. When no run holds two packs, the service compacts the newest single layer that holds several packs. The service also writes the v2 index `<pack id>.idx` of the new pack, so every pack has its own index. That index names each object once, at the offset of its first copy, and its CRC fields are zero. A pack is named by the SHA-256 of its bytes, like any pack. The service adds the pack rows after the swap.
- Reserve. A merge or a compaction reserves its working memory from the memory budget before it reads: 28 bytes for each record, and for a compaction also the bytes of the new pack, the largest source pack and 4 MiB, and for a compaction that splits, twice the bytes of the source packs, 400 bytes for each object and 32 MiB for the resolution of a delta more. A run whose split would need more than half of the memory budget is copied, as a run of class `b` is.

Retire. A merge or a compaction records the files that it frees in the table `pack_retired` (`RetireFiles`), each with the time, and then swaps the manifest in one step: the new layer replaces the run. A compaction frees the layer files, and the `.pack` and `.idx` of each source pack that no other layer holds. A merge frees the layer files of the layers that are layer files, and never an `.idx` file. The records come first, so a crash never drops a file that is not recorded. The swap fails, and the new files stay unlisted, when the layers of the run changed since the plan. A maintenance pass deletes a retired file only when the grace has passed (`MOTTE_COMPACTION_GRACE`, default one hour) and the current manifest, which every replica reads, lists no layer or pack that holds it. The pass first reads the version of each due file (`bucket.Store.Version`), then marks each as deleting with the time (`BeginDelete`), which skips a file that another pass marked within the last 10 minutes and a file that was retired again after the grace cut, then reads the manifest, then deletes the object at the version that it read (`bucket.Store.Delete`), removes the pack row of a `.pack` file, and forgets the record (`ForgetRetired`). A file that is gone when the version is read needs no delete. A delete that returns `bucket.ErrChanged` keeps the file and its record, and a later pass takes it again. It forgets the record of a file that the manifest lists, and keeps the file. A writer that stores a pack file or a layer file under a name that may be retired calls `ClaimRetired` first, which removes the record when no collector marked it, so no collector takes the file. When a collector marked it already, the writer waits until the record is gone and then stores the file anew. The collector and the writer meet in the metadata store, so a file that a new layer holds is never deleted, with no lock between replicas. A pass that stops after the mark finishes the deletion once the mark is 10 minutes old. A pass that stalls for longer than that between its mark and its delete cannot delete a file that a writer stored again, on a backend with a conditional delete (`fs`, `gcs`): the stored-again file has a new version, and the delete refuses it. On `s3` the delete is not conditional, so `Maintain` deletes no retired file on a bucket that does not delete conditionally: it still compacts, merges and retires, keeps the due files and their records unmarked, writes a warning log line for the pass, and counts the kept files in `motte_retired_files_delete_skipped_total`. Retired files then pile up on `s3` until the keys of packs are unique. A file whose pack a layer holds is kept for both its `.pack` and its `.idx`. A request that began within the grace reads every object it started with, because the old packs and layers are still there. Every crash leaves the manifest valid: the files of an unfinished merge or compaction are unlisted, named by content, and the next run of the same work writes the same files.

Rollback and contract. The layered index is additive. This release writes the per-pack `.idx` and the pack row of every pack that it creates, compacted packs included, and a release before the layered index reads the repository from the pack rows and those indexes. A merge never deletes an `.idx`. Compaction deletes the `.pack`, the `.idx` and the pack row of a source pack together, after the grace, and the compacted pack that replaces it has all three. Dropping the legacy `.idx` write, and the pack rows as the source of the pack list, is a later release that follows a release that has run in production with the layered index.

## Data model

The tables below are the PostgreSQL schema. Every backend of `meta.Store` keeps the same fields. See Backends.

```
repos(path pk, name, owner, created_at)
packs(repo, pack_id, bytes, created_at, pk(repo, pack_id))
pack_manifests(repo pk, generation bigint, body, updated_at)   body is the manifest of the layered index
pack_retired(repo, key, retired_at, deleting_at, pk(repo, key))   files that wait for deletion
refs(repo, name, commit_sha, generation, updated_at, pk(repo, name)); sequence ref_generation
workspaces(id pk, repo, owner, epoch bigint, op, snapshot, report_generation, created_at, deleted_at)
op_heads(workspace_id pk -> workspaces, epoch, generation, heads text[], updated_at)
event_partitions(partition pk, seq, floor)   64 rows
events(partition, seq, repo, ref, old_commit, new_commit, generation, kind, at, pk(partition, seq))
protected_refs(repo pk, patterns text[])
subscriptions(id pk, url, secret, repo, created_at)
subscription_cursors(sub_id, partition, cursor, lease_owner, lease_until, pk(sub_id, partition))
land_queue(repo, id, seq, ref, base, head, expect_tree, kind, state, owner, result, generation, enqueued_at, done_at, pk(repo, id))   seq is unique and rises
land_leases(repo, ref, owner, lease_until, pk(repo, ref))
land_heads(repo, ref, n, pk(repo, ref))   rows ever logged
land_log(repo, ref, n, old_tip, new_tip, paths, pk(repo, ref, n))   paths is null for a change with too many
```

A repository text has the form `<prefix>:<path>`. The prefix `native` is reserved for the repositories that `POST /v1/repos` creates. The prefix matches `^[a-z0-9][a-z0-9-]{0,62}$`. The path has 1 to 512 bytes of UTF-8. Object keys are `repos/<prefix>/<base64url path>/...` and `ops/<workspace>/...`. A repository that the caller owns elsewhere has no `repos` row. The store keeps only the packs and refs of such a repository.

A ref generation comes from the sequence `ref_generation`. It is never reused, including when a ref is deleted and created again. A swap with `expect` 0 creates the ref.

### Epoch fence

`workspaces.epoch` is the highest epoch that the caller claimed.

- Claim: the PostgreSQL statement is `INSERT ... ON CONFLICT (id) DO UPDATE SET epoch = GREATEST(workspaces.epoch, EXCLUDED.epoch) WHERE deleted_at IS NULL RETURNING epoch, op, snapshot`. A claim below the stored epoch answers 409 `vcs_claim_lost`. A claim on a deleted workspace answers 410. `owner` and `repo` are set once. A different value answers 409.
- A claim needs `epoch` of 1 or more. A claim on a `native` repository that has no row, or whose `repos.owner` differs from `owner`, answers 403 `vcs_repo_forbidden`. A claim whose `owner` or `repo` differs from the stored value answers 409 `vcs_workspace_conflict`. A claim on a deleted workspace answers 410 `vcs_workspace_deleted`.
- Write: in PostgreSQL, every ref swap, ref delete and op-heads swap is one statement. It starts with `WITH guard AS (SELECT id FROM workspaces WHERE id = $ws AND epoch = $epoch AND deleted_at IS NULL FOR SHARE)`. The write applies only when the guard row exists. A workspace report is one `UPDATE` of the workspace row with the same epoch, repository and `deleted_at` conditions in its `WHERE`. It takes the row lock itself, because two reports that hold `FOR SHARE` and then update the row can deadlock.
- In PostgreSQL, the claim `UPDATE` takes the row lock that `FOR SHARE` conflicts with. In every backend, a write in flight finishes first, and every later write of the old epoch fails. `vcs_claim_lost` wins over `vcs_generation_conflict`. An op-heads write also needs `op_heads.epoch <= $epoch`.
- A `node` route compares the grant epoch with `workspaces.epoch` before it runs, for reads and writes. A missing or deleted workspace answers 401. A repository that differs from `workspaces.repo` answers 403 `vcs_repo_forbidden`. A different epoch answers 409 `vcs_claim_lost`. Every write statement also needs `workspaces.repo` to equal the grant repository.

### Raise before commit

The caller raises the epoch before it commits its own increment. The caller calls claim with the next epoch, then commits the increment. A failed claim fails the step before the commit, and the step retries. Claim is idempotent. `GREATEST` keeps the highest of two racing claimers. If the commit then loses to another claimer, that claimer raises again. A raise with no commit refuses only the writes of an epoch that the caller already replaces. A workspace of the new epoch, and so its first grant, does not exist before the raise.

### Workspace state

`op`, `snapshot` and `report_generation` live on `workspaces`. A node report and a flush write one row with one ordering rule: the higher `report_generation` wins, and an equal one writes again, because a flush at the generation of a report carries a newer `snapshot`. A flush with generation 0 writes only while the stored `op` equals `prev`. A write that loses on this ordering rule answers success and changes nothing. A flush runs under the same epoch fence as a node write: a stale `epoch` answers 409 `vcs_claim_lost`, a deleted workspace 410, and an unknown workspace 404. A flush answers 204.

### Delete

`DELETE /v1/workspaces/{id}` sets `deleted_at`. Every later read and write of that workspace fails. The call is idempotent, answers 204, and does nothing for an unknown workspace. The store removes no op-head row and no object.

### Repository creation

`POST /v1/repos` creates the repository with one root commit under the ref `main`. The root commit has the empty tree, the author and committer `motte <motte@motte.invalid>` and the creation time as its time. The store writes the root objects first, then the `repos` row and the ref in one transaction, so a failed create leaves no repository without `main`. The path is `repo_` and random base32 text. The name is trimmed and has 1 to 100 bytes with no control character, else 400 `invalid_body`. A workspace can start on `main` at once.

## Backends

A caller of the service chooses where the service keeps its state. Two seams hold it. `meta.Store` keeps the small mutable records. `bucket.Store` keeps the immutable objects. The server and `internal/store` depend only on these two interfaces and on their neutral types and errors. A backend is a Go type that implements one of them. The operator writes or picks a backend, and `cmd/motte` builds the server from it. The server needs no change.

| Interface | Holds | Backends |
|---|---|---|
| `meta.Store` | Repositories, workspaces and their epoch fence, op heads, refs, protected ref patterns, ref events, event subscriptions, the land queue, lease and log, the pack listing. | `meta/postgres`, `meta/sqlite` |
| `bucket.Store` | Pack files, pack indexes, layer files and op objects. | `bucket/gcs`, `bucket/s3`, `bucket/fs` |

The suites `meta/metatest` and `bucket/buckettest` export `Run(t, newBackend)`. A backend passes its suite before a server uses it. The suite is the executable form of this section, and a difference between them is a defect.

### Contract of meta.Store

Every method that writes is one atomic unit. The unit is one conditional statement, or one atomic batch of statements, or one read-write transaction. No method needs a transaction that spans calls, a row lock that the caller holds, or a read whose result changes the write. The database decides each condition. This is the weakest set that a backend can offer: a database with atomic batches and no interactive transactions, such as Cloudflare D1, meets it.

- Fence: the fence of workspace `ws` at `epoch` and `repo` holds while the workspace row has that id, that epoch and that repo and is not deleted. A write that needs the fence checks it in the same unit as the write. A claim and a write are ordered. A write that is ordered after the claim sees the raised epoch and fails.
- Failed condition: a write whose condition fails changes nothing. The backend then reads the workspace row, and the ref or op-heads row when the method names it, and picks the error. `meta.Fence` holds the precedence, so every backend gives the same one: `ErrClaimLost` wins over a generation conflict. These reads are not part of the unit. The error answers for a state that is at least as new as the write attempt.
- Generation: the generation of a ref is positive and unique in the store. No ref ever takes a generation that was taken before, including a ref that is deleted and created again. The backend takes it from one counter in the unit of the write. A generation is not ordered across refs, and a failed write can skip one.
- Order: names, repositories, pack ids and workspace ids are opaque text. A list sorts them by byte value of their UTF-8 text.
- User tokens: `meta.UserTokenStore` keeps the SHA-256 hex of a token, never the token. `CreateUserToken` answers `ErrExists` for a repeated ID or hash. `RevokeUserToken` keeps the first revocation time and answers `ErrNotFound` for an unknown ID. `UserTokens` lists newest first, ties by ID descending.
- Time: `Repo.CreatedAt` and the creation time of a pack come from the clock of the backend, with a resolution of 1 millisecond or finer.
- Racers: of N concurrent calls that need the same free condition, exactly one wins and the others get the error of a lost condition.
- Events: every write that creates, moves or deletes a ref appends one event in the same unit as the ref write, and a write that changes nothing appends none. The event holds the repo, the ref, the old and new commit (empty when absent), the generation (that of the deleted ref for a delete), the writer kind and the time. The kind is `node` for `SwapRef` and `DeleteRef`, `merge` for `MergeRef` and `MergeDeleteRef`, the `kind` argument for `UpdateRef`, and `operator` for the `main` that `CreateRepo` writes.
- Partitions: a store has `meta.Partitions` = 64 event partitions. The partition of an event is `meta.Partition(repo, ref)`: the FNV-1a 32-bit hash of the repo, a zero byte and the ref name, modulo 64. The backend gets the partition as an argument, so no SQL computes it. All events of one ref are in one partition. Changing the number is a migration that renumbers the events.
- Event order: each partition has its own counter, taken in the unit of the write. An event is identified by `(partition, seq)`. In a partition `seq` starts at 1, has no gap, and follows commit order: a reader that sees `seq` N sees every event of that partition below N, so a consumer that keeps the last `seq` of each partition loses no event. This gives the order of the events of one ref. There is no order across partitions. Writes to refs in different partitions share no counter and do not wait for each other.
- Retention: retention removes events and keeps, for each partition, the highest removed `seq` as a floor. A read of a partition from a `seq` below its floor is `ErrEventsPruned`. The other partitions are not affected.
- Lease: the lease of a partition of a subscription is columns of its row in `subscription_cursors`. A lease write is one conditional statement on that row, and `now` is an argument, so the clock of the caller decides expiry. The lease passes to a new owner only when `lease_until` is at or before `now`. Owners must have clocks that differ by much less than the lease time. A subscription has one lease and one cursor for each partition.
- Land queue: `EnqueueLand` inserts an item with the next `seq`, in the state pending, and a repeat of a repo and id returns the stored item. The `seq` order is arrival order, and two items that arrive at once have no fixed order. The `result` and `generation` of an item are set only by `LandRef` and `FinishLands`, and an item that is done never changes.
- Land lease: the lease of a ref is one row of `land_leases`. A lease write is one conditional statement, and `now` is an argument, so the clock of the caller decides expiry. The lease passes to a new owner only when `lease_until` is at or before `now`, and the owner may renew it. `ClaimLands`, `LandRef` and `FinishLands` apply only while the owner holds the lease at `now`.
- Land unit: `LandRef` is one atomic unit with the conditions that the lease is held and the ref is at the old commit. It moves the ref with a new generation, appends one event, adds the rows of the batch to `land_log` with the next `n` of `land_heads`, removes the rows older than `meta.LandLogRetention` rows, and ends the items of the batch. A condition that fails changes nothing. The backend then reads the lease and the ref, and picks the error: `ErrLeaseHeld` wins over `*RefConflict`.
- Visibility: a method that returns nil has committed durably. A read that starts after it sees the write, in every client of the store.

### Contract of bucket.Store

- `Create(key, data)` writes `data` when no object has `key`, and returns true. It returns false and changes nothing when an object has `key`. Of N concurrent creators of one key, exactly one gets true. A stored object is never replaced.
- `Version(key)` returns an opaque name of the object as it is now, or `bucket.ErrNotFound`. A backend with a conditional delete gives a stored-again object a new version, even with the same bytes.
- `Delete(key, version)` removes the object when its version is `version`, and is not an error for a missing key. When the object has another version, it stays and `Delete` returns `bucket.ErrChanged`. A backend without a conditional delete removes the object whatever its version, and it says so: a `Store` may declare `bucket.Caps{ConditionalDelete, Hedged}` with the method `Caps() bucket.Caps`, and `bucket.CapsOf(Store)` returns them. A wrapper has the method `Unwrap() bucket.Store`, and `CapsOf` follows it through every layer that declares no `Caps`: `Hedged` is true when any layer declares it, and `ConditionalDelete` is the answer of the outermost layer that declares `Caps`. A `Store` with no declaring layer has no capability. `bucket/gcs` and `bucket/fs` declare `ConditionalDelete`, `bucket/s3` does not, `bucket.Hedge` declares `Hedged` with the `ConditionalDelete` of its primary store, and `bucket.Observe` only unwraps. `bucket.DeletesConditionally(s)` is `CapsOf(s).ConditionalDelete`. The suite `buckettest` checks that `CapsOf(store).ConditionalDelete` equals `buckettest.Caps.ConditionalDelete`. Only the deletion of a retired file calls it. A `Create` of a deleted key writes again.
- `Get(key)` returns the whole object. `GetRange(key, off, n)` returns up to `n` bytes from `off`, fewer at the end, none when `off` is at or past the end, and the rest of the object when `n` is negative. A missing key is `bucket.ErrNotFound` for both.
- A read that starts after a `Create` that returned sees the whole object. The `fs` backend keeps its on-disk format: a 4096-byte header block, then the data.

### Provided backends

- `meta/postgres` is the production backend. It keeps the schema in the section Data model, applies `meta/postgres/migrations` at start under an advisory lock, and meets each write with one statement, except a ref write, `CreateRepo` and `LandRef`. The fence of a ref or op-heads write is a `FOR SHARE` read of the workspace row inside the statement. A report is one `UPDATE` that locks the row itself. The generation comes from the sequence `ref_generation`. A ref write, `CreateRepo` and `LandRef` are one transaction. It first takes the next event number of the partition with `UPDATE event_partitions SET seq = seq + 1 WHERE partition = $1 RETURNING seq`. The row lock lasts to the commit, so `seq` order is commit order in the partition, and the number comes before any workspace lock, so a claim is not starved by writes that wait for the counter. One statement then writes the ref and the event, and the transaction rolls back when no row changed, so a failed write leaves no gap. Only writes to refs of the same partition wait for each other. `LandRef` takes the event number the same way, then runs one statement of data-modifying parts: the lease check, the ref move, the event, the log rows, the prune and the item results, all of them conditional on the ref that moved. A land lease write and a claim are one statement.
- `meta/sqlite` is for tests and for a service that runs with no other process. It keeps the same fields in the tables of `meta/sqlite/migrations`. It uses a pure Go driver, so the service builds with CGO disabled. It opens one connection, so its writes are ordered, and one process uses one database file. Each write is one transaction of statements in which no read feeds a write. The fence is an `EXISTS` condition of the statement. The generation comes from the row `ref_generation` of the table `counters`, which the same transaction increments. A ref write inserts its event first, with the condition of the ref write, and the number `event_partitions.seq + 1`. A second statement raises `event_partitions.seq` only when that event row exists. The ref write follows with its own condition. A write whose condition fails therefore leaves no event and no gap, in a batch that does not roll back too. `LandRef` follows the same pattern: its event insert carries the lease and ref conditions, and each later statement (the log row of each land and the end of each item, one statement for each) needs that event row to exist for the generation of the unit. Times are integer microseconds, and the heads are JSON text.
- `bucket/gcs`, `bucket/s3` and `bucket/fs` are the object backends. `gcs` reads through a pool of clients (`gcs.NewPool`, `MOTTE_GCS_CLIENTS`): each client has its own HTTP transport, so one connection pool and one set of stream locks serve only a share of the readers, and a read takes the clients in turn. Writes, versions and deletes use the first client. The `gcs` backend also hedges its range reads (`bucket.Hedge`, "The Tail at Scale"): a range read that outlasts the 95th percentile of the recent reads of its size class (at most 64 KiB, at most 1 MiB, larger), held between `MOTTE_GCS_HEDGE_MIN` and `MOTTE_GCS_HEDGE_MAX`, starts one duplicate on one more client, which only duplicates use and so is never one of the connections that stalled the first read. The first success wins and the loser is cancelled; a first answer that is an error other than a missing key waits for the other read. The budget of the duplicates stays held until both reads have ended, also when one wins. A token bucket allows duplicates for at most `MOTTE_GCS_HEDGE` percent of the reads, with a burst of 10, so a slow bucket cannot double the load. A duplicate of a range of n bytes holds 3 times n of a budget of 16 MiB of its own, apart from the read budget, and a read that finds no token or no budget waits for its first read alone. A read of a whole object, and of a range above a third of the budget, has no duplicate. `gcs` writes with the precondition that the object does not exist, and its version is the generation, which `Delete` sends as `ifGenerationMatch`. `fs` links a synced temporary file to its name, and its version is the generation in the header block, which is unique for each `Create`. `fs` checks the version and removes the file under one lock of the root, which `Create` takes for its link.
- `bucket/s3` uses the AWS SDK for Go v2, and only `bucket/s3` imports it. `s3.NewClient` builds the client from the endpoint, region and addressing style. `Create` is `PutObject` with `If-None-Match: *`. An answer of 412 is `created` false. An answer of 409 (`ConditionalRequestConflict`, a concurrent write of the same key is in flight) is retried, and the retry answers 412 or succeeds, so exactly one creator gets true. The retries are bounded: `Create` makes at most 8 attempts, and waits between them on the clock of the package `internal/clock`, for a random time between half of and all of 20 ms doubled for each retry and capped at 1 s. After the eighth answer of 409, `Create` returns an error that wraps it. A wait ends early with the error of the context. `Get` and `GetRange` are `GetObject`, and `GetRange` sends a `Range` header: `bytes=off-` for a negative `n` or an end that overflows, otherwise `bytes=off-(off+n-1)`. An `n` of 0 reads the first byte of the range and returns none, so a missing key is still `bucket.ErrNotFound`. An answer of 416 is an empty result, and `NoSuchKey` is `bucket.ErrNotFound`. A negative `off` is an error. The client sends checksums only where the API needs them, because some S3-compatible services reject the default checksum headers. S3 reads see a completed write, so the read-after-`Create` rule holds. A service must support `If-None-Match` on `PutObject`: AWS S3, R2 and MinIO do. A service that ignores the header breaks the rule that a stored object is never replaced, and `buckettest` shows it. `Version` is the ETag from `HeadObject`. `Delete` ignores the version: `DeleteObject` takes `If-Match`, but a file that a writer stores again has the bytes of the deleted file, so it has the same ETag, and the precondition cannot tell them apart. `buckettest.Caps{ConditionalDelete}` is true for `fs` and `gcs` and false for `s3`, and the suite tests the refusal of a stale version only where it is true.

### A new backend

A backend implements the interface and returns the sentinel errors of its package. It does not map them to wire codes: the server does. It adds a test that calls `metatest.Run` or `buckettest.Run` with a constructor that returns an empty store. It adds a branch to `cmd/motte` that chooses it from the environment. The backends below are not in the repository. Each paragraph states how the backend meets the contract.

- Cloud Spanner (`meta`): each write is one read-write transaction. The transaction reads the rows that the condition names, tests the condition, writes, and commits. Spanner orders transactions strictly, so a claim and a write are ordered. The generation counter is one row that the transaction updates, or a Spanner sequence, which is unique and not ordered. The creation time is the commit timestamp. Reads that pick an error are strong reads. The heads are an `ARRAY<STRING>`.
- Cloudflare D1 (`meta`): each write is one `batch` call. D1 runs a batch as one transaction and rolls it back when a statement fails. D1 has no interactive transaction and no row lock, and the contract needs neither. The conditions are the `WHERE` clauses and `INSERT ... SELECT ... WHERE EXISTS` fences of `meta/sqlite`, which is SQLite SQL. The counter is a row that the first statement of the batch increments. The result of a statement reports the rows that it changed, and a conditional statement that changed no row is the failed condition. Reads that pick an error go to the primary.
- Cloudflare R2 (`bucket`): `bucket/s3` serves R2 with `MOTTE_S3_ENDPOINT` set to the account endpoint of R2 and `MOTTE_S3_REGION=auto`. It needs no other backend.

## jj backend

The crate `jj/` builds the binary `jj`: jj 0.47.1 (`jj-lib` and `jj-cli`, pinned exactly) with four shims and the subcommand `jj motte`. The binary keeps the name `jj` because it is jj with extra stores. A release attaches it for linux amd64 and arm64, with sha256 sums. `go run ./internal/release/cmd/release jj` builds it and `publish` sends it (see Release entry points).

### Shims

| Shim | Registered name | Role |
|---|---|---|
| `Backend` | `motte-objects` | Reads and writes git objects through the workspace daemon. |
| `OpStore` | `motte-op-store` | jj's simple op store, with the objects mirrored to the daemon. |
| `OpHeadsStore` | `motte-op-heads` | Op heads in local files, swapped into the store with a generation. |
| `WorkingCopy` | `motte-vfs` | A working copy on a kernel overlay over the lazy lower layer of the daemon. |

The names are written into `.jj/repo/*/type` and `.jj/working_copy/type`. A rename is a migration.

The backend writes the bytes of `GitBackend::write_commit` (the `change-id` and `jj:trees` headers, the signing path, and the retry that lowers the committer time when a commit ID exists with other extras) and git trees in git entry order. A commit ID is the git SHA. `jj/tests/differential.rs` proves that the object IDs equal those of stock `GitBackend`. The working copy reads the dirty set of the daemon instead of walking the tree. `.jj` is a symlink in the mount to a directory outside it. `set_sparse_patterns` is unsupported.

### Daemon channel

The shims speak to the workspace daemon with the control protocol (see Control protocol) over a unix socket. The socket is the path in `MOTTE_VFS_SOCK`, or else the path in the file `store/ctl_sock` of the repo directory, which `init` writes. One function finds it. A command that finds none fails and names both places. The one exception is the update of the op heads, which then skips the remote heads, warns, and marks nothing as unsynced.

A shim branches on the `code` of an error answer. It reads the `err` text only of an answer that has no `code`, which a daemon released before the code sends (see Control protocol); one function holds that fallback. The shim hashes every object itself and refuses an answer whose SHA differs. An operation or a view that it reads back with `getop` must hash (blake2b-512 of its content, as jj's op store names it) to the ID it asked for. A daemon that is not in overlay mode fails every command that needs the dirty set.

The shim refuses an object over 16 MiB before it sends one byte: a snapshot of a file over that size fails and names the path and the limit. A request that gets no answer is sent once more only when sending it twice has the effect of sending it once. A `swapref` or an `opheads` swap is never sent again on a lost answer: the shim reads the ref or the heads. The change landed when the stored state is the one the request wanted, it is sent again when the stored generation is still `expect`, and it lost the race otherwise. The code `line_too_long` is an answer and is never retried.

Every request carries the W3C `traceparent` of the innermost open span, or the `TRACEPARENT` environment variable. With `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` set, the binary exports OTLP over HTTP or HTTPS, with no retry: one span `jj.command` for each command and one for each operation (`jj.motte.snapshot`, `jj.snapshot`, `jj.checkout`, `jj.read_tree`, `jj.write_commit`, `jj.op_heads.update`, `jj.push`, `jj.fetch`), with the counts `objects` and `bytes`. `OTEL_SDK_DISABLED=true` or `OTEL_TRACES_EXPORTER=none` turns tracing off. A span holds no path, file content or credential. The command keeps its finished spans in memory and opens no network connection. When it ends, it starts a detached copy of its own executable in an export mode, writes one OTLP request to the standard input of the copy and exits at once. It never waits for the copy. The copy has its own session, no standard output or error, and no other open file, so a caller that reads the command output to its end does not wait for it. The copy sends one POST and exits. It sends to `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` as given, or else to `OTEL_EXPORTER_OTLP_ENDPOINT` followed by `/v1/traces`. It sends the headers of `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_EXPORTER_OTLP_TRACES_HEADERS`, trusts the system roots and the file `SSL_CERT_FILE`, uses the proxy of `HTTPS_PROXY` (with the credentials of its URL) unless `NO_PROXY` names the host, and stops after `OTEL_EXPORTER_OTLP_TIMEOUT` milliseconds (default 10 000). A failure is silent. A snapshot sends blobs with `putbatch`, at most 64 blobs or 8 MiB a request, and falls back to `put` on the code `unknown_op`.

### Op heads

`opheads` without `heads` reads the op heads of the workspace; a store `vcs_not_found` before the first write is generation 0 and no heads. With `heads` it swaps them when the stored generation is `expect`. Each update of `motte-op-heads` first reads the remote heads, so a writer whose claim is lost fails with `vcs_claim_lost` before its local write. It then writes the local heads, removes from the remote set the replaced operations and every remote head that the local op store holds and the local heads do not, adds the new head and swaps. On `vcs_generation_conflict` it reads the winning heads and applies its update again. All daemon calls of one update share a budget of 2 seconds. A daemon that answers the code `unknown_op` leaves the remote heads behind the local ones and the command succeeds. Any other store failure, or a spent budget, does the same and also adds the new head to the marker `motte_unsynced` in the repo directory. A lost claim at the swap fails the command after the local write.

### Subcommands

`jj motte` has the subcommands `init`, `restore`, `attach`, `verify`, `flush`, `sync`, `snapshot`, `changes`, `push`, `fetch` and `dirty`. `init`, `restore` and `attach` need the `base_tree` of the daemon to be the tree of the mount commit. Every jj command except `jj motte snapshot`, and the ones that never snapshot (`--ignore-working-copy`), holds a shared flock on `motte_command.lock` in the repo directory until it exits. `jj motte snapshot` holds the lock exclusive through its snapshot and skips with `busy` when a command holds it. `jj motte flush` waits for the lock at most 45 seconds and then fails, so that it ends before the caller that runs it.

`jj motte changes` prints the work-tree diff as JSON for a caller that sets `HARNESS_CHANGES_SCOPE` (`branch` or `uncommitted`), `HARNESS_CHANGES_BASE` and `HARNESS_CHANGES_PATCH_BYTES` (default 1 MiB). It loads the op head that ended last, in whole seconds, then the larger ID. It never snapshots and writes no operation. It diffs the target tree against the daemon base tree and overrides each path that `changes` names. The patch is in git format and ends at the last whole file within the byte cap, with `truncated` set. A file larger than 2 MiB is `large` with no hunk. Renames are not detected.

### Push and fetch to a git origin

A workspace has a git origin when `init` or `restore` got `--origin-url`, an http(s) URL with no user information, and `--commit` or `--base`, which set the repo config key `motte.origin-base` to the commit that origin holds. `--origin-branch <name>` makes, at the start commit, the local bookmark `<name>` and the tracked bookmark `<name>@origin`, and sets `revset-aliases.'trunk()'` to `"<name>"@origin`. The only remote is `origin`. The commands keep a bare repo `motte_git` in the repo directory as the transport, run the `git` binary over HTTPS with `GIT_TERMINAL_PROMPT=0`, and share a deadline of 10 minutes.

`jj motte push -b <bookmark>...` refuses a missing or conflicted bookmark, a new commit that is conflicted, has no description or is the root commit, a rewrite of the default branch of origin, and a workspace with no daemon socket. It probes the claim with `opheads`, reads the tips of origin (`git ls-remote --symref`), fetches the base of each bookmark by SHA with no blobs (falling back to heads at depth 20, 200, 1,000, then unshallow), writes the loose objects of the new commits from the daemon, probes the claim again, and runs `git -c pack.window=0 push --atomic --force-with-lease=refs/heads/<name>:<commit of NAME@origin>`. `pack.window=0` stops the delta search, so the push sends full blobs and never reads a delta base blob that `motte_git`, a blob-less partial clone, lacks. `--no-thin` does not do this: over smart HTTP git ignores it and still makes a thin pack. One jj transaction then sets `NAME@origin`. A bookmark whose tip already equals its commit is recorded without an update. The span `jj.push` carries `remote`, `refs` and `outcome`: `ok`, `refused`, `stale`, `rejected`, `network` or `claim_lost`. A daemon call that fails with `vcs_claim_lost` at any step of a push or a fetch ends the command as `claim_lost`, and any other daemon failure ends it as `network`.

`jj motte fetch [-b <bookmark>...]` probes the claim, reads the heads of origin (at most 100 without `-b`, the default branch first), clears `refs/motte/origin/` and `refs/motte/base/` of `motte_git`, and fetches the heads that differ into `refs/motte/origin/` with `--no-tags --no-filter --depth=N`, `N` being 1, 20, 200 and 1,000 (`--refetch` when a `refs/motte/base/` ref existed). A commit whose parent is in neither `motte_git` nor the daemon at depth 1,000 is a shallow root: the backend records it in the `shallow` file, published whole under an exclusive lock on `shallow.lock`, and shows it with no parents. The command refuses a commit whose `encoding` header is not UTF-8. It writes the new commits to the daemon with `putbatch`, parents first, each after the blobs and trees that differ from its first parent. One jj transaction makes the tips heads and sets `NAME@origin`. A local bookmark moves to the tip when `NAME@origin` is tracked, the local target equals the old `NAME@origin` and the old commit is an ancestor of the tip, or when neither existed. The span `jj.fetch` has the outcomes of push except `stale`.

### Push and fetch to a native repository

A native workspace has no git origin: the store is the origin. `init` and `restore` take `--origin-native`, which excludes `--origin-url`, and set `motte.origin-native` to true and `motte.origin-base` to the start commit. `--origin-default-branch` requires it and sets `motte.origin-default-branch`. A native workspace without `motte.origin-base` or `motte.origin-default-branch` makes push, fetch and delete fail as `refused`; none falls back to a git origin. A ref of the store is a bookmark of `origin`. The commands run no `git` and make no network call of their own. They need no flush, because `put`, `putbatch` and `snapshot` answer after the upload to `POST /v1/vcs/objects`.

`jj motte push -b <bookmark>...` refuses what the git push refuses, and a rewrite of the default branch or the start branch: the stored tip must be an ancestor of the commit. The new commits are the ancestors of the bookmarks that are not ancestors of `motte.origin-base` or a `NAME@origin`, at most 1,000 for each bookmark. The steps are:

1. Probe the claim with `opheads`.
2. Read the ref of each bookmark with `refs` and `name`.
3. Check that the store holds the new commits, their trees and their blobs, comparing each commit only with its first parent and reading only trees whose ID differs. Blobs are asked with `has`; a daemon that answers `unknown op` gets `getbatch` with a size limit of one byte. A missing object stops the push as `network`.
4. Probe the claim again.
5. In name order, send `swapref` with `expect` set to the stored generation, or 0 to create the ref. A ref that is at the commit needs no swap. A ref that differs from the commit that `NAME@origin` records ends the push as `stale` with "origin moved NAME; run jj motte fetch first". `vcs_generation_conflict` is `stale`. `vcs_claim_lost` is `claim_lost`.
6. One jj transaction sets `NAME@origin`, tracked, for each bookmark that the store holds at the commit.

The swaps are not atomic across refs: the first failure stops the push, and the error names the bookmarks that this call moved. There is no force option: a rewrite is a compare-and-swap against `NAME@origin`. `jj motte push --delete NAME` (repeatable, never with `-b`) deletes refs of a native repository only. It refuses the default branch and the start branch, and a name with no ref and no `NAME@origin`. It ends as `stale` when the stored commit differs from the commit that `NAME@origin` records. It forgets `NAME@origin` without a swap when the ref is already gone, sends `swapref` with `delete` for the rest, and forgets `NAME@origin` of the deleted refs in one transaction. The local bookmark stays.

`jj motte fetch [-b <bookmark>...]` probes the claim, lists the refs with `refs`, and takes the named bookmarks, or the default branch and the first 99 others in name order. It refuses a named bookmark with no ref and no `NAME@origin`. A bookmark with no ref but with a `NAME@origin` was deleted: the command forgets `NAME@origin`, keeps the local bookmark and prints `NAME: deleted on origin`. For each other bookmark it reads the commit with `get` and refuses a missing commit or an object that is not a commit. It walks the commits that the jj index lacks, at most 1,000 for each bookmark, with the shallow-root rules of the git fetch. One jj transaction adds the roots to the `shallow` file, makes the tips heads and sets `NAME@origin` with the local-bookmark rules of the git fetch.

### Human identities

A person uses `git` on the git routes with no grant in one of two ways, and neither needs a vendor. Each is a `identity.Authenticator`, tried after the grant. The same rules apply to both: a person never holds `merge`, `operator`, `import` or `node`, never mints a grant and never reaches a route except git and repository creation. A `write` person pushes as a `write` grant does, so a protected ref refuses it (see Protected refs). A deployment that gives `write` protects the default branch of each repository, so that only the control plane lands it with a `merge` grant.

OIDC identity (`internal/identity/oidc`). The service verifies a JWT from the issuer that `MOTTE_OIDC_ISSUER` names. It trusts no header that is not a valid JWT.

- The JWT must use an algorithm of `MOTTE_OIDC_ALGS`, be signed by a key of the key set (a request refreshes the cache when it is 45 minutes old, and a `kid` that the cache does not hold causes a fetch; there is at most one fetch at a time and one a minute, and a fetch holds no lock, so the cached keys serve until the fetch ends; a cache that is 1 hour past its last good fetch is refused, so a failed refresh has 15 minutes of retries before any sign-in is refused), with `iss` equal to the issuer, `aud` holding the audience, `now < exp`, `nbf <= now` and a non-empty value in the claim `MOTTE_OIDC_CLAIM`. When that claim is `email` and the token carries `email_verified` as false (the boolean, or the text `false`), the token is refused; a token with no `email_verified` is accepted, because an identity-aware proxy verifies the email itself. Any failure answers 401 like a refused grant.
- The rules (`MOTTE_OIDC_RULES`) map the claim value to a scope on the repository of the URL. When several rules match, `write` wins. No matching rule answers 401.
- The result is the claims of a grant with the scope, the repository of the URL and the claim value as `subject`. It is never a signed grant.
- Cloudflare Access is one configuration, not a separate implementation: `MOTTE_OIDC_HEADER=Cf-Access-Jwt-Assertion`, `MOTTE_OIDC_ISSUER=https://<team>.cloudflareaccess.com`, `MOTTE_OIDC_AUDIENCE=<AUD tag>` and `MOTTE_OIDC_KEYS_URL=https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`.

Per-user tokens (`internal/identity/usertoken`). They need no issuer. An administrator with an `operator` grant issues one with `POST /v1/tokens`, or `motte token create --principal P --scope S [--repo R]... [--ttl D]`. A person cannot issue one, whatever the identity.

- A token is `mtu_` and 43 characters of base64url from 32 random bytes. The response shows it once. The service keeps the SHA-256 hex of it with the principal, the scope, the repositories, the expiry and the revocation time (`user_tokens`). The record has an ID `ut_<16 hex>`.
- The scope is `read` or `write` with at least one repository, or `admin` with none. A token with `admin` creates a repository (`POST /v1/repos` accepts it as an `operator` grant) and nothing else. A token answers only for the repositories that it lists.
- A token is accepted as `Authorization: Bearer <token>` or as the password of HTTP Basic, so `git clone https://user:<token>@host/git/<path>.git` works. A token that is unknown, revoked or past its expiry answers 401.
- `motte token list` and `motte token revoke ID` call `GET /v1/tokens` and `DELETE /v1/tokens/{id}`.

The command `motte login` runs the OAuth device authorization flow (RFC 8628) against the issuer of `MOTTE_OIDC_ISSUER`, with the client of `MOTTE_OIDC_CLIENT_ID`. It reads the endpoints from the discovery document, polls the token endpoint with `slow_down` and `authorization_pending` handled, and saves the ID token (else the access token) in `<user config dir>/motte/login.json` with mode 0600. `motte login --print` prints it for `git -c http.extraHeader="Authorization: Bearer $(motte login --print)"`. `motte repo create` and `motte token` use it when `MOTTE_TOKEN` is unset. `motte repo create [--owner OWNER] NAME` prints the path of the new repository.

## Grant

A grant is `mg1.<base64url payload>.<base64url signature>`. The payload is JSON. The signature is Ed25519 over the base64url payload text. The encoding has no padding.

| Claim | Meaning |
|---|---|
| `kid` | Key identifier. The verifier selects the public key by `kid`. |
| `scope` | One of `node`, `read`, `write`, `import`, `operator`, `merge`. |
| `refs` | Ref patterns, at most 64: a ref name, or a prefix that ends in `*`. Only a `merge` grant carries them. A `merge` grant with `refs` moves only the refs that a pattern matches, on every path that moves or deletes a ref: a land (`ref`), `PUT` and `DELETE` of a ref, and each command of a git push. A ref that no pattern matches answers 403 `vcs_repo_forbidden` on a land and a ref route, and `ng <ref> not in the grant` for a push command, and the other commands of the push go on. A `merge` grant with no `refs` still moves any ref. Refusing it is a later step, after every service that mints a `merge` grant sends `refs`. |
| `ws` | Workspace identifier. |
| `epoch` | Claim epoch of the workspace when the grant was minted. |
| `repo` | Repository text. |
| `owner` | Owner of the workspace. |
| `subject` | The creator, for traces only. It grants nothing. |
| `exp` | Expiry as Unix seconds. A grant is valid while `now < exp`. |

Required claims by scope: `node` needs `ws`, `epoch` and `repo`. `read`, `write`, `import` and `merge` need `repo`. `operator` needs none.

The verifier holds only public keys. Each key has a `kid` and a set of allowed scopes. The verifier rejects a grant whose scope is not allowed for its key. Every rejection answers 401 with the same error, and the response never carries the grant. A valid grant whose scope a route does not serve answers 403 `vcs_repo_forbidden`; a grant that is not valid answers 401. The same rule holds for every route, including the git routes.

### Keys

The caller owns the private keys. Two signers exist:

- The control-plane key may sign all scopes. A `write` grant lets the bearer move any ref of its repository without a workspace: only the control plane or a trusted pipeline holds one.
- The node key lives on the node daemon and may sign only `node`. A compromised node cannot mint `import`, `operator` or `merge` grants. The plugin mints a `node` grant only for a pod of an allowed namespace (see Node plugin). It can mint `node` grants, bounded by the repository and epoch of the workspace row.

### Rotation

1. Add the new public key to the store.
2. Switch the signer to the new key.
3. Remove the old key after the longest grant life: 1 hour for `node`, 60 seconds for `operator`, `read`, `write`, `import` and `merge`.

Both keys are valid between step 1 and step 3.

### Read authorization

Authorization happens at claim time. For a repository that the store keeps (it has a `repos` row), claim checks `repos.owner` against `owner`. For any other repository, the caller checks that the creator may read it and signs the claim. The store trusts that and binds the workspace to the repository.

## Versioning

The path prefix `/v1` is additive. New fields and new routes are allowed, and clients ignore unknown fields. A breaking change gets `/v2`, served beside `/v1`. The module is tagged with semantic versions.

Wire error codes keep their `vcs_` text: `vcs_claim_lost`, `vcs_events_pruned` (410), `vcs_generation_conflict`, `vcs_land_conflict` (409), `vcs_land_invalid` (400), `vcs_land_stale` (409), `vcs_land_timeout` (504), `vcs_not_found`, `vcs_object_invalid`, `vcs_object_too_large`, `vcs_ref_protected` (403), `vcs_repo_forbidden`, `vcs_workspace_conflict`, `vcs_workspace_deleted`. Three codes have no prefix: `unauthorized` (401), `invalid_body` (400) and `internal_error` (500). `method_not_allowed` (405) answers a method that its path does not serve. A panic in a handler is logged with its stack and answers 500 `internal_error` when the handler sent no status yet. The error body is `{"error":{"code","message","details"}}`. A conflict on a ref carries the stored ref in `details.ref`.

## Client

Package `client` has one typed method for each route of both planes. A `Client` sends one grant. The caller gives a `GrantFunc` that the client calls before each request, so a caller holds one `Client` for each scope that it uses.

- Each call has a time budget of 2 seconds, which `WithBudget` changes. A deadline on the call context that is earlier than the budget wins.
- The client injects the W3C trace context of the call context into the request headers.
- The client follows no redirect. A 3xx answer is the error `ErrRedirect`, and the grant goes to no other host.
- A failure answer is an `*Error` with the HTTP status, the wire code, the message and the details. `errors.Is` matches the sentinel of the code: `ErrNotFound`, `ErrGenerationConflict`, `ErrClaimLost`, `ErrObjectInvalid`, `ErrObjectTooLarge`, `ErrRefProtected`, `ErrEventsPruned`, `ErrLandConflict`, `ErrLandInvalid`, `ErrLandTimeout`, `ErrRepoForbidden`, `ErrWorkspaceConflict`, `ErrWorkspaceDeleted`, `ErrUnauthorized`, `ErrInvalidBody` and `ErrInternal`. A failure answer with no wire error body is `ErrUnexpected`.
- `CurrentRef` returns the stored ref that a ref generation conflict carries, and `ConflictPaths` returns the paths that a land conflict names.
- `Land` serves a `merge` client and a `write` client. Its time limit is 35 seconds (`DefaultLandBudget`), which is above the 30 seconds that the server waits, unless `WithBudget` sets another.
- `SwapRef` and `DeleteRef` serve a `node` client and a `merge` client. `SetProtectedRefs`, `ProtectedRefs`, `Events`, `CreateSubscription`, `Subscriptions` and `DeleteSubscription` serve an `operator` client.

Package `testserver` runs the real server in the process of a test, on a fresh schema of the PostgreSQL database that the caller names (or `MOTTE_TEST_DATABASE_URL`) and a temporary filesystem bucket. It skips the test when no DSN is set and no throwaway cluster can start (see Tests), or fails it when `MOTTE_TEST_REQUIRE_PG=1`. It returns the base URL, the pool of its schema (for a test that sets up a state no route can make), the metadata store, the bucket and the verifier (for a test that runs a second replica on the same state), the control-plane and node signers, and helpers that mint operator, node, read, write, import and merge grants. `testserver.New(t, ...Option)` starts a server on SQLite by default, with the options `WithPostgres(dsn)` (PostgreSQL), `Required()` (a missing database fails the test), `Template(path)` (SQLite from a copy of a migrated database file) and `WithLimits(testserver.Limits)` (lower size limits for the test; the limits are process-wide, so a test that sets them takes no part in a parallel test that sends large bodies). No public option names an internal type. It does not run the delivery worker. A land needs no worker: a request starts the leader in the process of the server.

## Observability

- Traces: OTLP, with the endpoint from the environment and no vendor in the code. Span names start with `vcs.serve.` and end with the route, such as `vcs.serve.put.refs`. Requests accept W3C trace headers.
- Spans below the span of a request exist only when the request is traced. Each carries the counts of what the request read from the store while the span ran: `objects`, `bytes`, `layers_probed`, `range_reads`, `range_read_bytes`, `range_cache_hits` and `range_cache_misses`. A bucket read has no span of its own; the counts are on its parent. A read that takes 500 ms or longer gets the span `vcs.pack.read.slow` (`offset`, `range_bytes`, `bytes`), at most one each second.
  - Fetch: `vcs.fetch.has_wants` and `vcs.fetch.has_haves` (negotiation), `vcs.fetch.commit_walk`, `vcs.fetch.edge_trees`, `vcs.fetch.tree_walk` and `vcs.fetch.pack_write`. Each starts where the last ended.
  - Land: `vcs.land.enqueue` and `vcs.land.wait` (`leader_here`) under the request, and `vcs.land.warm` for the read-ahead of a waiting land. The leader records `vcs.land.batch` (`items`) as a root span that counts the reads of the batch, with `vcs.land.merge` for each land (`expect_tree`, `outcome`: `noop`, `fast_forward`, `rebase` or the error code, `commits`), `vcs.land.write` and `vcs.land.swap` (`rows`, `conflict`); a conflict of the swap adds the event `ref_moved` and the batch tries again.
  - Mount reads: `vcs.treebulk` (`max_entries`, `trees`, `entries`, `batches`, `fill_sizes_ms`, the time that the blob headers took).
  - Maintenance, each as a root span that no request sampling drops, and only when it did work: `vcs.maintain.compact` (`layers`, `class`, `bytes_written`, `objects`), `vcs.maintain.merge` (`layers`, `class`, `tail`, `objects`), `vcs.maintain.graph_build` and `vcs.maintain.graph_merge` (`commits`, `graph_bytes`), and `vcs.maintain.collect` (`files`, `deleted`).
- A failed span records the Go type of the error as the event `exception` with `exception.type`, and never the error text, which can name a path or an object key.
- OTLP metrics: with the endpoint set, the metrics of `/metrics` also go over OTLP, with the same names and values. `/metrics` stays.
- Profiles: `MOTTE_PPROF` serves `/debug/pprof` on its own listener and never on the public port.
- Metrics: Prometheus at `/metrics`, with names that start with `motte_`: `motte_http_requests_total` and `motte_http_request_duration_seconds`, by route, and the open-pack cache: `motte_pack_cache_hits_total`, `motte_pack_cache_misses_total`, `motte_pack_cache_evictions_total`, `motte_pack_cache_open_packs`, `motte_pack_cache_open_bytes`, `motte_bucket_index_read_bytes_total`, `motte_bucket_range_reads_total` and `motte_bucket_range_read_bytes_total`. Every read of the bucket, also an index read, is timed: `motte_bucket_read_duration_seconds`, a histogram by `op` (`get` or `get_range`) for the reads that succeed, and `motte_bucket_read_errors_total`, by `kind` of failure (`timeout`, `5xx` or `other`). With hedging on, `motte_bucket_hedges_total`, `motte_bucket_hedge_wins_total` and `motte_bucket_hedges_skipped_total` count the duplicates that started, the duplicates that answered first, and the slow reads that got no duplicate. A missing key and a read that its caller cancelled are neither. The layer cache: `motte_index_cache_hits_total`, `motte_index_cache_misses_total`, `motte_index_cache_evictions_total` and `motte_index_cache_bytes`. Maintenance: `motte_compaction_runs_total`, `motte_compaction_bytes_total`, `motte_compaction_objects_total`, `motte_layer_merge_runs_total`, `motte_layer_merge_objects_total`, `motte_retired_files_deleted_total`, `motte_retired_files_delete_skipped_total`, `motte_maintenance_failures_total`, and the layers of the repositories that maintenance has seen: `motte_manifest_layers_max`, `motte_manifest_layers_sum` and `motte_manifest_repos`. The span of a store request has the attribute `layers_probed`.
- Logs: JSON. A request that its client abandoned before the answer ends with status 499 and an INFO line that names the route, not an `internal_error` and an ERROR line. A log line of the service never holds a grant, a path or an object body. A log line of the node daemon never holds a grant, and it carries the error text of its own process, which can name a node path.
- Instrumentation is additive. It never changes behavior or errors.

## Virtual workspace daemon

The packages under `internal/vfs` are the node daemon of the virtual workspace. `cmd/motte-vfsd` runs it. It reads and writes the store plane with a `node` grant, so a workspace holds no store credential. The FUSE server and the overlay build on Linux only. On other systems `motte-vfsd` prints a message and exits 1. The daemon writes JSON logs, and `OTEL_EXPORTER_OTLP_ENDPOINT` enables trace export. A client span name is `vcs.client.` and the route, such as `vcs.client.ref.swap`.

| Package | Role |
|---|---|
| `internal/vfs/store` | Store client, tree and blob types, and the node cache. |
| `internal/vfs/lower` | The FUSE lower layer, and the dirty set and changes of the upper directory. |
| `internal/vfs/ctl` | The control protocol and its socket. |
| `internal/vfs/csi` | The CSI node plugin, the mount steps and the `mountinfo` reader. |
| `internal/vfs/importer` | `import`: fetch with `git`, pack, upload. |
| `internal/vfs/materialize` | `materialize`: write the checkout of a commit. |
| `internal/vfs/tel` | Correlation, spans, log records and the health record. |
| `internal/vfs/upperdir` | The scan of the upper directory. |

`HTTPStore` is the store client of the daemon. It is `client.Client` with the spans of the daemon, so it follows no redirect, trims a trailing `/` of the base URL, and matches errors with `errors.Is` on the sentinels of `client`. It answers a `vcs_repo_forbidden` answer with `ErrGrantRefused`, which no retry passes. A call has no budget of its own; the timeout of the HTTP client bounds it. A grant that fails to mint fails the call, and no request leaves with an empty token. A test drives `HTTPStore` against the real service.

### Commands

| Command | Meaning |
|---|---|
| `motte-vfsd mount` | Standalone, for a host that has `fusermount`; `csi` mounts with `mount(2)`. Serves the tree of one commit as the read-only lower layer of a kernel overlay. Needs `-api`, `-commit`, `-mnt`, `-upper` and `-ctl-sock`, and `MOTTE_VFS_GRANT` in the environment. It does not refresh the grant. |
| `motte-vfsd csi` | The CSI node plugin. Needs `-api`, `-grant-key-file` and `-allowed-namespaces` (comma-separated, no wildcard). Flags `-driver` (default `vfs.motte.dev`), `-endpoint`, `-node-id`, `-state`, `-uid` and `-gid`. |
| `motte-vfsd materialize` | Writes the checkout of a commit to `-dest`. A marker file records a finished checkout, and a later run changes nothing, whatever commit it names. |
| `motte-vfsd import` | Fetches a repository with `git`, packs it and uploads it with an `import` grant (`PUT /v1/vcs/packs/{pack_id}`). `-depth 0` imports the whole history as packs of about 48 MiB and skips the ranges that the store holds. |

The key file of `csi` is JSON `{"kid","key"}`. `key` is the standard base64 of an Ed25519 private key or of its 32-byte seed. The store must trust the public key for the scope `node`. The plugin signs a `node` grant for each store call. The grant names the workspace, the claim epoch and the repository of the volume attributes, and it expires after one hour (`internal/vfs/nodegrant`). A publish whose claims are incomplete, such as epoch 0, fails.

### Mount mode

The FUSE mount is the read-only lower layer. Every mutating operation answers `EROFS`: `mkdir`, `symlink`, `create`, `unlink`, `rmdir`, `rename`, `setattr`, `write`, `fallocate`, and an `open` with a write flag. `fsync` answers success. Entry, attribute and negative timeouts are one hour, because the lower never changes while the mount lives. A lookup reads trees in bulk (`GET /v1/vcs/trees/{sha}`). The first read of a file reads its blob and the blobs that follow it in tree order in one batch (`POST /v1/vcs/blobs/batch`). A node cache that all workspaces on the node share keeps the blobs. The cache is keyed by SHA only: the control op `getbatch` serves a cached blob to any workspace that names its SHA, whatever its repository.

`mount` refuses to start without `-upper` and `-ctl-sock`. It binds the socket before it mounts. It runs `upperdir.ProbeTrustedBeside` first and fails with a `CAP_SYS_ADMIN` error when the process cannot read `trusted.*` attributes on the file system of the upper directory. The probe uses a new sibling directory and never writes into the upper directory.

The control socket lies in a directory that no other workspace can reach. The daemon refuses a directory that is open to others, creates the socket with mode 0660 and gives it to the uid and gid of the mount.

### Node plugin

The plugin implements the identity and node services of the CSI spec on a unix socket.

Trust boundary: the volume attributes of a workspace volume come from the pod spec, so a pod names its own workspace, epoch and repository. The plugin signs a `node` grant for whatever those name. It therefore serves only the pods of the namespaces in `-allowed-namespaces`, which the kubelet reports as `csi.storage.k8s.io/pod.namespace`. `NodePublishVolume` refuses a request whose pod namespace is missing (`InvalidArgument`) or not listed (`PermissionDenied`), for a workspace volume and a control socket volume alike, and an empty list refuses every pod. The control plane that creates the pods and the namespaces in the list are trusted to name the right workspace; the plugin does not check a claim against the store. The chart runs it as a privileged DaemonSet with `hostPID`, and its kubelet pods directory propagates to the host. `csi` refuses to start unless it shares the PID namespace of the node and has another mount namespace. The `CSIDriver` sets `attachRequired: false`, `podInfoOnMount: true` and the lifecycle mode `Ephemeral`. A restart of the plugin ends the mounts that it serves, so the DaemonSet updates with `OnDelete`.

`NodePublishVolume` of a workspace volume runs these steps in order:

1. Refuse a volume id with `,`, `:`, `\` or `/`. Read the `mountinfo` of the plugin and of one process of each other mount namespace.
2. Run `ProbeTrustedBeside` on `<vol>/upper`.
3. Unmount a stale overlay at the target, then a stale lower at `<vol>/lower`. `EBUSY` answers `Unavailable`. While any overlay with `upperdir=<vol>/upper` is mounted anywhere, the publish fails with `Unavailable`.
4. Discard `upper` when it has entries and `<vol>/base` is missing or names another commit. Recreate `work`, create `upper`, and write `<vol>/base` (write `base.new`, `fsync`, rename, `fsync` of `<vol>`).
5. Open the VFS, bind the control socket, mount the lower at `<vol>/lower`, serve the socket, and mount overlayfs at the target with `lowerdir=<vol>/lower,upperdir=<vol>/upper,workdir=<vol>/work,redirect_dir=on,metacopy=on,index=off,xino=off,nfs_export=off`.

A failure in step 5 undoes the earlier steps in reverse order. A publish for a volume that the plugin serves returns OK and changes nothing. The control socket of a workspace lies in `ctl/<hash>` of the state directory, where `<hash>` is 32 hex digits of the SHA-256 of `<pod UID>/<workspace>`, so the socket path stays under the 107 bytes of Linux for any pod UID and workspace. A publish fails with `InvalidArgument` and names the path when the state directory makes it longer. The directory has mode 0700, owned by the uid and gid of the mount, so a pod with two workspace volumes has two sockets. The pod UID comes from the kubelet, so a pod cannot name the directory of another pod, and a publish without it fails. A second volume for the same workspace in the same pod fails with `FailedPrecondition`. A volume with the attributes `volume=ctl` and `workspace` binds that directory at its target, in either publish order.

`NodeUnpublishVolume` unmounts the overlay, reads the `mountinfo` again, and fails with `Unavailable` while an overlay still references `<vol>/upper`. Only then it unmounts the lower (lazily only when the plain unmount fails), stops the socket and closes its connections, closes the VFS, and deletes the control directory of the workspace and `<vol>`. The plugin holds no lock across an unmount, a `mountinfo` read or a delete: a call for a volume that another call works on fails with `Aborted`, and no volume waits on another. It never runs `stat` on `<vol>/lower`, because a dead FUSE answers `ENOTCONN`. The directories `upper` and `work` live on the disk of the node with the lifetime of the volume. Only `NodeUnpublishVolume` deletes them.

### Volume attributes

Package `volume` is the public contract between a caller and the plugin. A workspace volume has the attributes `workspace`, `epoch`, `repo`, `commit` and `runtime`. A workspace is 1 to 64 characters of `A-Za-z0-9_-`, because it names a directory. `runtime` only labels telemetry. `ParsePublication` rejects a missing workspace or repository and a commit that is not a SHA-1. The control socket volume has `volume=ctl` and the `workspace` of the volume whose socket it binds. The workspace sees the socket at `volume.CtlDir/volume.CtlSocket` (`/run/motte-vfs/ctl.sock`), and `MOTTE_VFS_SOCK` names it. The CSI driver name is a flag of `csi` and the chart value `driverName`.

### Control protocol

The daemon answers each line of the unix socket with one line. A request is a JSON object with `op`, the fields of the op, and an optional `traceparent`. A request line over 64 MiB is answered with the code `line_too_long`, and the connection stays open. The daemon closes every connection when its mount ends.

A success answer holds exactly the fields that the table names. A field is never omitted, and a list is `[]` when it is empty. An answer with no fields is `{}`. An error answer is `{"err", "code"}`, with `ref` on a lost ref swap. `err` is for people, and a consumer branches on `code`. The `err` text always contains the `code` text, except for `unknown_op`, whose text is `unknown op`. A shim released before `code` matches these substrings (`too_large`, `unknown op`, `not found`, `vcs_claim_lost`, `vcs_generation_conflict`, `vcs_not_found`), so a daemon keeps them for as long as such a shim is deployed. A daemon and a shim are deployed apart, so a shim also talks to a released daemon that sends no `code` and may omit `gen` and `heads` of `opheads` at generation 0. The shim reads an answer with no `code` by those same substrings and reads the missing fields as generation 0 and no heads. This compatibility window ends when no deployed daemon omits the code. The codes:

| code | Cause |
|---|---|
| `invalid_request` | The line is no JSON object, or a field is missing, malformed or over a limit. |
| `unknown_op` | The op does not exist, or the daemon cannot answer it. |
| `line_too_long` | The request line is over 64 MiB. |
| `store_unavailable` | The store call got no answer, or an answer that is no wire error. |
| `internal_error` | The daemon failed on its own side, such as a read of the upper directory. |
| `vcs_object_too_large` | An object is over 16 MiB, or a `getbatch` answer would pass 16 MiB, or the store answers 413 (see Limits and memory). |
| `vcs_not_found`, `vcs_generation_conflict`, `vcs_claim_lost`, `vcs_object_invalid`, `vcs_repo_forbidden`, `vcs_workspace_conflict`, `vcs_workspace_deleted`, `unauthorized`, `invalid_body`, `method_not_allowed` | The wire code of the store answer. |

| op | request | answer |
|---|---|---|
| `get` | `sha` | `type`, `data` (base64) |
| `put` | `type`, `data` (base64) | `sha` |
| `putbatch` | `objects`: list of `{type, data}`, at most 4096 | `shas`, in request order |
| `has` | `shas`, at most 4096 | `present`: one bool for each name, from `POST /v1/vcs/objects/has` |
| `opheads` | `expect`, `heads` (both optional) | `gen`, `heads` |
| `refs` | `name` (optional) | `refs`: list of `{name, commit, generation}` without `name`; `ref` with `name` |
| `swapref` | `name`, `expect`, `commit`, or `delete: true` with `expect` of at least 1 | `ref`; `{}` after a delete; on a lost swap the error answer carries the stored `ref`, when one exists |
| `putop` | `type` (`operations` or `views`), `sha`, `data` (base64) | `{}` |
| `getop` | `type`, `sha` | `data` (base64) |
| `getbatch` | `shas`, at most 4096, `max_size` (optional) | `datas` in request order; `large`: indices of blobs over `max_size`, whose `datas` entry is empty |
| `workspace` | `sha` (the head operation), `commit`, `generation` | `{}` |
| `changes` | none | `boot`, `token`, `base_tree`, `changes`: list of `{path, status, old_sha, old_mode, old_size, new_sha, new_mode, size}` |
| `dirty` | none | `boot`, `token`, `base_tree`, `entries`: list of `{path, kind, exec, opaque}` |
| `token` | none | `boot`, `token`, `base_tree` |
| `stats` | none | cache counters `blob_hits`, `blob_misses`, `tree_calls` (numbers) |

`opheads` without `heads` reads the op heads: generation 0 and no heads before the first write. With `heads` it swaps them when the stored generation is `expect`. The objects in `changes` and `entries` omit a field that is zero or empty. `put` and `putbatch` name each object by the hash of its bytes. `swapref` with `expect` 0 creates the ref. A ref name is a valid ref name, and a commit is 40 lowercase hex digits.

Call statistics: the `vfs.stats` log record of a workspace (every 30 s, and once when the workspace closes) holds, for each kind of call with at least one call in the interval, the fields `<kind>_count`, `<kind>_total_us` and `<kind>_max_us`: the number of calls, the sum of their time and the longest one. Nothing is sampled. A control call has the kind `ctl_<op>`, with `<op>` the op of the request (`unknown` for an op that the protocol does not name). A store request that a control call makes has the kind `store_<route>`, such as `store_op_heads_swap`, `store_op_put` or `store_object_put`; the route is the name of its client span without the prefix `vcs.client.`, with `.` as `_`. A store request that a FUSE operation makes has no such kind. The time of a control call includes the time of its store requests, and the interval of a record ends the counts of the calls that finish in it, so a call that spans two records is in the second.

The fixtures in `testdata/ctl` pin the table. A file `<group>.json` is `{"group", "steps"}`. A step is `{"name", "request" or "raw", "answer"}` and may have `"given"`. A consumer opens one connection to a fresh daemon for each file and replays the steps in order. It sends `request` as one line, or `raw` as one line of text, and compares the answer line with `answer`. Objects match key for key, with no key missing or surplus, and lists match element for element. The string `"*"` in an answer matches any value that is present. `given` names a state of the upper directory that only the daemon under test sets up, and other consumers ignore it. `edited` is an upper directory with `a` rewritten and `n` added over the base tree of the fixtures; `clean` is the empty upper directory. The Go tests replay every file against the real socket, the real service and a lower layer on an in-memory upper directory. A shim and its fake replay the same files.

### Dirty set

The daemon builds the dirty set from a walk of the upper directory with the `trusted.overlay.*` attributes, always against the base tree of the mount. `upperdir.Scan` applies these rules:

| Upper entry | Dirty set |
|---|---|
| Regular file or symlink | `file` or `symlink`, with `exec` from the upper mode |
| Fifo, socket or device that is no whiteout | Nothing when the base lacks the path, else `deleted` |
| Whiteout | `deleted` when the base has the path |
| Directory with `trusted.overlay.opaque=y` | `dir` with `opaque` when the base has the path; its children are new |
| Directory that only holds entries | Nothing for the directory; its changed children |
| Empty upper directory that the base lacks | `dir` |
| File with `trusted.overlay.metacopy` | Nothing when it lies at its own base path, its redirect names that path and its exec bit equals the base; else `file` |
| Entry with `trusted.overlay.redirect` | The origin is the base path in the value. The merged children are the origin subtree plus the upper children. |
| Directory over a base file, file over a base directory | `dir` with `opaque`, or `file` |

A directory that merges a base directory at another path lists every base leaf below the origin at its new path, and `Origin` names the base path of the content. The root entries `.jj` and `.git` are skipped. The result is sorted by path. A submodule is an empty directory in the mount.

`OSFS` opens each directory once, one component at a time, and checks with `fstatat` and `fstat` that each opened inode is the directory that `lstat` found, so a swapped-in symlink is never followed. `changes` takes the base side from the base tree. It hashes the bytes of an upper file only when the base has its path, at most 2 MiB for each file and 64 MiB in all.

### Change token

`token` and `dirty` return `<boot>:<fingerprint>`. The fingerprint comes from an `lstat` walk: the entry count, the newest change time, the sum of the sizes of the regular files, the sum of the change times and the sum of the inode numbers. A walk is settled only when the newest change time is at least 50 ms older than the start of the walk. An unsettled walk returns a token that equals no other token. `ScanStable` reads the token, scans, reads the token again, and retries up to 3 times while two settled tokens differ. The daemon runs no `syncfs`. A store through a mapping that is already dirty changes no token, so a consumer forces a snapshot at intervals.

### Release entry points

The release of an artifact does not depend on a CI provider. The command `go run ./internal/release/cmd/release` is the only code that builds or publishes a release artifact. A CI workflow is a caller: it sets inputs and runs the command, and it holds no build logic. The command needs `docker` with `buildx`, and `gh` only for the `github` destination.

| Command | Effect |
|---|---|
| `image -name N -repo R [-version V] [-push] [-platforms P] [-file F] [-build-arg K=V] [-dry-run]` | Runs `docker buildx build` of `images/N/Dockerfile` (or `F`) for `P` (default `linux/amd64,linux/arm64`). `-version` must be semver. It tags `R:X.Y.Z` and, for a version that is not a prerelease, `R:X.Y`. Without `-push` it only builds, and it loads the image when `P` names one platform. With `-push` it needs `-version`, adds provenance (`mode=max`) and SBOM attestations, and pushes. |
| `jj -out DIR [-arch amd64\|arm64] [-src jj] [-dry-run]` | Builds `jj` in the pinned Debian bookworm Rust image for `linux/ARCH`, runs `jj --help` in the pinned Debian bookworm base image, and writes `DIR/jj-linux-ARCH` and `DIR/jj-linux-ARCH.sha256`. |
| `publish -dir DIR -dest D [-tag T] [-dry-run]` | Sends every file of `DIR` to `D`. `github` attaches them to the release of `T` through `gh`, and creates the release when it is missing. `dir=PATH` copies them to `PATH`. Each destination is an implementation of `publish.Publisher`. A destination that the command does not know is sent by the caller from `DIR`, which holds plain files. |

`REGISTRY_USERNAME` and `REGISTRY_PASSWORD` make `image -push` run `docker login` for the registry host of `R`. When `REGISTRY_PASSWORD` is unset, the caller has signed in already. The registry host and path are inputs, never literals in code or in a chart default.

GitHub is one caller. The workflow `image.yml` reads the repository variables `IMAGE_REGISTRY` (default `ghcr.io`), `IMAGE_NAMESPACE` (default the repository owner, lowercased) and `REGISTRY_USERNAME` (default the actor), and the secret `REGISTRY_PASSWORD` (default `GITHUB_TOKEN`). With none set it pushes `ghcr.io/<owner>/motte` and `ghcr.io/<owner>/motte-vfsd`. The workflow `jj-release.yml` builds each architecture on a native runner and publishes to the destination in the variable `JJ_RELEASE_DEST` (default `github`).

A consumer of the `jj` binary takes the download base URL as a setting and fetches `<base>/jj-linux-<arch>` and `<base>/jj-linux-<arch>.sha256`. The release does not fix the base. For the `github` destination it is `https://github.com/<owner>/<repo>/releases/download/<tag>`.

### Tests

The packages under `internal/vfs` pin the daemon over an in-memory upper directory, the plugin over a fake of the mount seam, the control protocol fixtures against the real service, and `HTTPStore` against the real service. `internal/vfs/upperdir` tests `Scan` against a model of overlayfs and, as root, against a real overlay.
